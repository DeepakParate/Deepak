Standard Operating Procedures

Detailed step-by-step procedures for VMware administration, Windows Server management, and cloud infrastructure tasks — built from real enterprise experience.

VMware

vSphere, NSX, vSAN, Horizon, and lifecycle management procedures

ESXi Host Deployment

VMware · Infrastructure
  1. Boot from ISO: Mount ESXi ISO via iDRAC/iLO virtual media, boot server
  2. DCUI Setup: Configure management network (IP, subnet, gateway, DNS) via DCUI
  3. Enable SSH: Activate SSH and ESXi Shell for remote management
  4. NTP Config: Set NTP servers for time synchronization
  5. vCenter Add: Add host to vCenter, join datacenter and cluster

vCenter Server Appliance Deployment

VMware · Management
  1. Stage 1 Setup: Mount vCSA ISO, run installer UI, select Install deployment type
  2. Target Selection: Connect to ESXi host, specify VM name and credentials
  3. SSO Configuration: Create SSO domain (vsphere.local) or join existing
  4. Network Settings: Assign static IP, FQDN, DNS servers, gateway
  5. Stage 2 Complete: Configure time sync, SSH access, CEIP, and verify services

HA/DRS Cluster Setup

VMware · High Availability
  1. Create Cluster: Right-click datacenter → New Cluster, name and enable HA/DRS
  2. HA Settings: Set admission control policy (% reserved capacity or failover hosts)
  3. DRS Automation: Configure automation level (Manual/Partial/Fully Automated)
  4. Add Hosts: Drag ESXi hosts to cluster, verify network and shared storage
  5. VM Overrides: Set per-VM HA/DRS rules for critical workloads

Distributed Switch Configuration

VMware · Networking
  1. Create vDS: Actions → New Distributed Switch, select version and uplink count
  2. Add Hosts: Right-click vDS → Add/Manage Hosts, select physical adapters
  3. Port Groups: Create distributed port groups for VLANs (Mgmt, VM Network, vMotion)
  4. Uplink Policy: Configure load balancing (Route based on IP hash/originating port)
  5. Security: Enable promiscuous mode if needed, set MAC address changes policy

vSphere Lifecycle Manager (vLCM)

VMware · Patching
  1. Enable vLCM: Select cluster → Updates → Lifecycle Manager → Enable
  2. Import Image: Upload ESXi ISO to vLCM depot or use online depot
  3. Create Baseline: Define desired image with patches, drivers, firmware
  4. Remediate: Check compliance, schedule remediation during maintenance window
  5. Validate: Verify all hosts compliant, check hardware compatibility issues

ESXi Patching Procedure

VMware · Maintenance
  1. Pre-Patching: Take VM snapshots, verify backups, check HCL compatibility
  2. Maintenance Mode: Put host in maintenance mode, evacuate VMs via vMotion/DRS
  3. Apply Patch: Use esxcli software vib install or vLCM remediation
  4. Reboot & Verify: Reboot host, check SSH/services, validate datastore connectivity
  5. Exit Maintenance: Exit maintenance mode, remove snapshots, monitor alerts

P2V & V2V Migration

VMware · Migration
  1. Assessment: Check disk space, network bandwidth, application dependencies
  2. VMware Converter: Install agent/agentless, configure source and destination
  3. Migration: Start conversion, monitor progress, handle VSS snapshots
  4. Post-Migration: Install VMware Tools, reconfigure network, update DNS/DHCP
  5. Validation: Test application functionality, decommission old server

VMware NSX Micro-Segmentation

VMware · Security
  1. NSX Preparation: Deploy NSX Manager, configure transport zones and edge nodes
  2. Logical Segments: Create overlay segments for application tiers (web/app/db)
  3. DFW Rules: Configure Distributed Firewall with micro-segmentation policies
  4. Security Groups: Create dynamic groups based on VM tags, OS type, or apps
  5. Monitor Traffic: Use NSX Intelligence/Flow Monitoring for traffic visualization

VMware Horizon VDI Setup

VMware · VDI
  1. Infrastructure: Deploy Connection Servers, configure load balancing
  2. Golden Image: Create and optimize Windows master image, install Horizon Agent
  3. Desktop Pools: Configure instant/linked clone pools with replica settings
  4. App Volumes: Deploy App Volumes Manager, create AppStacks for app delivery
  5. User Access: Configure entitlements, set up Unified Access Gateway for remote access

vSAN Configuration

VMware · Networking
  1. Prerequisites: Verify minimum 3 ESXi hosts, each with at least one SSD and one HDD/NVMe disk group
  2. Enable vSAN: Select cluster → Configure → vSAN → Turn On, choose between Hybrid or All-Flash mode
  3. Disk Groups: Claim disks per host — assign one cache tier (SSD) and one or more capacity tier disks per disk group
  4. Network Config: Create a dedicated VMkernel port (vmk) on each host tagged for vSAN traffic, ensure MTU 9000 for jumbo frames
  5. Storage Policy: Define VM Storage Policies in vCenter — set FTT (Failures to Tolerate) and RAID type (RAID-1/RAID-5/RAID-6)
  6. Health Check: Run vSAN Health Service, verify cluster, network, disk, and data tests all pass green
  7. Validate: Deploy a test VM on the vSAN datastore, check performance metrics via vSAN Performance Service

Snapshot Management

VMware · Infrastructure
  1. Pre-Snapshot Check: Verify VM has no existing snapshot chain older than 72 hours; confirm sufficient datastore free space (at least 20% of VM disk size)
  2. Take Snapshot: Right-click VM → Snapshots → Take Snapshot; provide a descriptive name/date, enable "Quiesce guest file system" for consistent state
  3. Validate Snapshot: Go to Snapshots → Manage Snapshots, confirm snapshot appears in the tree with correct timestamp and parent chain
  4. Monitor Delta Disk: Track delta VMDK growth via datastore browser; alert if delta exceeds 50% of base disk to avoid performance degradation
  5. Revert if Needed: Right-click snapshot → Revert to Snapshot to roll back VM state; power cycle VM post-revert and verify application health
  6. Delete & Consolidate: Remove snapshots via Delete All after changes are validated; confirm "Consolidate" option if disks show fragmentation warnings
  7. Post-Cleanup Validation: Verify VM snapshot tree is clean, datastore space is reclaimed, and VM performance metrics return to baseline

Windows

Windows Server administration, Active Directory, Group Policy, and security hardening

Windows Server Hardening

Windows · Security
  1. Disable Services: Turn off unnecessary services (Print Spooler, Remote Registry)
  2. GPO Policies: Apply CIS benchmarks via GPO (password policies, account lockout)
  3. Firewall Rules: Enable Windows Firewall, restrict inbound to required ports only
  4. Patch Management: Configure WSUS/SCCM, auto-install critical updates
  5. Audit Logging: Enable advanced audit policies, forward logs to SIEM

Windows Server Roles and Features

Windows · Administration
  1. Understanding Roles vs Features: Roles are primary services a server provides (AD DS, DNS, DHCP, IIS, Hyper-V); Features are supporting components (RSAT, .NET Framework, Failover Clustering) that extend role functionality
  2. Install via Server Manager: Open Server Manager → Manage → Add Roles and Features → Role-based installation → select server from pool → check desired roles and features → confirm and install
  3. Install via PowerShell: Use Install-WindowsFeature -Name AD-Domain-Services -IncludeManagementTools; list all available roles with Get-WindowsFeature and filter installed ones with Get-WindowsFeature | Where Installed
  4. Active Directory DS: Install AD DS role → run Install-ADDSForest to promote server to Domain Controller; configure site, replication, and SYSVOL after promotion
  5. DNS & DHCP Roles: Install DNS Server role for name resolution; install DHCP role, create scopes (IP range, subnet mask, gateway, lease duration), authorize DHCP server in Active Directory
  6. IIS Web Server Role: Install Web Server (IIS) role with required sub-features (ASP.NET, HTTP Redirection, Windows Auth); manage sites via IIS Manager or appcmd CLI
  7. Hyper-V Role: Install Hyper-V role (requires hardware virtualisation support); configure virtual switches (External/Internal/Private), create VMs, and enable Live Migration for HA scenarios
  8. Remove Roles & Features: Use Server Manager → Remove Roles and Features or run Remove-WindowsFeature -Name <FeatureName>; reboot if prompted and verify removal with Get-WindowsFeature

Windows Server Active Directory Setup

Windows · Active Directory
  1. Prerequisites: Assign a static IP to the server, set a proper hostname via System Properties, and ensure DNS is pointing to itself (127.0.0.1) before promoting to a Domain Controller
  2. Install AD DS Role: Open Server Manager → Add Roles and Features → select Active Directory Domain Services → include management tools → install and wait for completion
  3. Promote to Domain Controller: Click the notification flag in Server Manager → Promote this server to a domain controller; choose Add a new forest and enter your root domain name (e.g. corp.local)
  4. Configure Forest & Domain: Set Forest and Domain functional levels (Windows Server 2016 or higher recommended); set the Directory Services Restore Mode (DSRM) password and store it securely
  5. DNS & NetBIOS: Verify the DNS delegation warning (expected on new forests); confirm the NetBIOS domain name is auto-populated; ensure DNS role is installed alongside AD DS on the same server
  6. Prerequisites Check & Install: Let the wizard run the prerequisites check; resolve any warnings, then click Install — the server will reboot automatically to complete promotion
  7. Verify AD DS: After reboot, open Active Directory Users and Computers (ADUC) and DNS Manager; confirm the domain and default OUs (Computers, Users, Domain Controllers) are present
  8. Create OUs & Users: In ADUC, right-click the domain → New → Organizational Unit; create OUs for departments; add users with New-ADUser in PowerShell or via the ADUC GUI
  9. Join Clients to Domain: On client machines, set DNS to the DC's IP → System Properties → Change → enter domain name → provide Domain Admin credentials → reboot to complete domain join
  10. Group Policy Basics: Open Group Policy Management Console (GPMC); link a new GPO to the domain or an OU; configure password policies, logon banners, and software restrictions; run gpupdate /force to apply immediately

Install & Configure IIS

Windows · Web Server
  1. Install IIS Role: Open Server Manager → Add Roles and Features → select Web Server (IIS); include sub-features: Static Content, Default Document, HTTP Errors, ASP.NET, Windows Authentication, and Request Filtering
  2. Install via PowerShell: Alternatively run Install-WindowsFeature -Name Web-Server -IncludeManagementTools; add ASP.NET with Install-WindowsFeature Web-Asp-Net45
  3. Verify Default Site: Open a browser and navigate to http://localhost; you should see the IIS default welcome page confirming the service is running
  4. Create a New Website: Open IIS Manager → expand server node → right-click Sites → Add Website; set site name, physical path (e.g. C:\inetpub\mysite), binding (IP, port, hostname)
  5. Configure Application Pool: In IIS Manager → Application Pools → select or create a pool; set .NET CLR version and managed pipeline mode (Integrated); assign the site to the correct app pool
  6. Set Directory Permissions: Grant the app pool identity (IIS AppPool\PoolName) Read & Execute permissions on the site's physical folder via File Explorer or icacls
  7. Configure SSL/HTTPS: Import or request an SSL certificate via IIS Manager → Server Certificates; bind the certificate to the site on port 443; add an HTTP to HTTPS redirect rule via the URL Rewrite module
  8. Enable Windows Authentication: In IIS Manager → select site → Authentication; disable Anonymous Authentication and enable Windows Authentication for intranet apps requiring AD credentials
  9. Configure Logging: In IIS Manager → Logging; set log file format (W3C), log directory, and rollover schedule; logs are stored in C:\inetpub\logs\LogFiles by default
  10. Test & Monitor: Browse to the new site URL; use Failed Request Tracing for debugging 4xx/5xx errors; monitor performance counters via Performance Monitor or enable Application Insights for detailed telemetry

Windows Backup & Recovery Procedure

Windows · Disaster Recovery
  1. Install Windows Server Backup: Open Server Manager → Add Features → select Windows Server Backup; or run Install-WindowsFeature Windows-Server-Backup in PowerShell
  2. Plan Backup Strategy: Define RPO (Recovery Point Objective) and RTO (Recovery Time Objective); decide between Full Server backup, System State backup, or volume-level backup based on recovery requirements
  3. Configure Scheduled Backup: Open Windows Server Backup → Backup Schedule → Full Server or Custom; select backup destination (dedicated disk, network share, or remote volume); set daily or multiple-times-per-day schedule
  4. One-Time Backup: Use Backup Once for ad-hoc backups before patching or major changes; select Different Options to customise volumes and destination on the fly
  5. System State Backup: Run wbadmin start systemstatebackup -backupTarget:<drive> to back up AD DS, registry, SYSVOL, COM+ database, and boot files — critical for Domain Controller recovery
  6. Backup Verification: After each backup, check the Windows Server Backup event log (Event ID 4, 8, 14) for success/failure; periodically perform test restores to a lab environment to validate backup integrity
  7. File & Folder Recovery: Open Windows Server Backup → Recover → select backup date → Files and Folders; browse to the desired path and restore to original or alternate location
  8. Bare Metal Recovery: Boot from Windows Server installation media → Repair your computer → Troubleshoot → System Image Recovery; point to the backup location and follow the wizard to restore the full server image
  9. Active Directory Recovery: For AD restore, reboot DC into DSRM (F8 at boot); run wbadmin start systemstaterecovery; for authoritative restore of deleted objects use ntdsutil after non-authoritative restore completes
  10. Offsite & Cloud Backup: Configure Azure Backup (MARS Agent) for offsite copies — install the agent, register the vault, define backup policy and retention; verify recovery point creation in the Azure Recovery Services Vault portal

Linux

Linux server administration, shell scripting, and system management procedures

Linux File System Tree

Linux · Administration
  1. / (Root): Top-level directory — the starting point of the entire Linux file system hierarchy; all other directories branch from here
  2. /bin & /sbin: Essential user binaries (ls, cp, mv) and system binaries (fdisk, ifconfig) required for booting and single-user mode
  3. /etc: System-wide configuration files (network, users, services); critical files include /etc/passwd, /etc/fstab, /etc/hosts, /etc/ssh/sshd_config
  4. /var: Variable data that changes at runtime — logs (/var/log), mail spools, cron jobs, and package manager databases
  5. /home & /root: User home directories (/home/username) for personal files and settings; /root is the home directory for the root superuser
  6. /tmp & /opt: /tmp holds temporary files cleared on reboot; /opt stores optional third-party software packages installed outside the default tree
  7. /proc & /sys: Virtual filesystems exposing kernel and hardware info in real time — use cat /proc/cpuinfo, /proc/meminfo, and /sys for device tuning
  8. /dev & /mnt: /dev contains device files (disks, TTYs, null); /mnt and /media are standard mount points for external drives and network shares

Linux Permission

Linux · Security
  1. Understanding Permissions: Every file has three permission sets — Owner (u), Group (g), Others (o); each with Read (r=4), Write (w=2), Execute (x=1) rights
  2. View Permissions: Run ls -l to list permissions; output format is -rwxr-xr-- where the first char is file type, followed by three triads (owner/group/others)
  3. chmod (Symbolic): Use chmod u+x file to add execute for owner, chmod g-w file to remove write from group, chmod o=r file to set others to read-only
  4. chmod (Numeric): Use octal notation — chmod 755 file sets rwxr-xr-x; chmod 644 file sets rw-r--r--; chmod 700 file restricts access to owner only
  5. chown & chgrp: Change file owner with chown user:group file; use chown -R user:group /dir for recursive ownership changes on directories
  6. Special Permissions: Set SUID (chmod u+s) to run as file owner, SGID (chmod g+s) to inherit group, Sticky Bit (chmod +t) on directories to restrict deletion to file owners only
  7. umask: Set default permission mask with umask 022 (new files get 644, directories get 755); add to /etc/profile or ~/.bashrc to persist across sessions
  8. ACL (Advanced): Use setfacl -m u:username:rwx file for fine-grained access beyond standard UGO; verify with getfacl file

File Systems Concept

Linux · Storage
  1. What is a File System: A file system defines how data is stored, organized, and retrieved on a disk — it manages inodes (metadata), data blocks, and directory structures
  2. Common Types: ext4 (default on most Linux distros — journaled, stable), XFS (high-performance, large files), Btrfs (snapshots, checksums), tmpfs (RAM-based, volatile), NFS (network-mounted)
  3. Inodes & Blocks: Each file has an inode storing metadata (permissions, owner, timestamps, pointers to data blocks); check inode usage with df -i and block usage with df -h
  4. Create a File System: After partitioning, format with mkfs.ext4 /dev/sdb1 or mkfs.xfs /dev/sdb1; use blkid to verify the UUID and type of the new file system
  5. Mount & Unmount: Mount with mount /dev/sdb1 /mnt/data; unmount with umount /mnt/data; verify active mounts using mount | grep sdb1 or lsblk
  6. Persistent Mounts (/etc/fstab): Add entry — UUID=xxxx /mnt/data ext4 defaults 0 2; test without rebooting using mount -a and check for errors
  7. Check & Repair: Run fsck /dev/sdb1 on unmounted partitions to detect and fix errors; use tune2fs -l /dev/sdb1 to inspect ext4 superblock details
  8. Disk Usage & Quotas: Monitor usage with du -sh /path and df -h; enable disk quotas via quotaon and define limits with edquota -u username to control per-user consumption

Install & Configure YUM

Linux · Package Management
  1. Check Existing YUM: Verify if YUM is already installed by running yum --version; YUM is pre-installed on RHEL, CentOS 7, and Amazon Linux — if found, proceed to configuration steps
  2. Install YUM (if missing): On minimal installs, run sudo rpm -ivh yum-*.rpm using the RPM from your distro's ISO, or bootstrap with sudo dnf install yum -y on RHEL 8/9 where DNF is the default
  3. Verify Package Manager: Confirm installation with which yum (should return /usr/bin/yum) and check version details via yum --version
  4. Configure YUM Repos: Repo files live in /etc/yum.repos.d/; each .repo file defines a repository with [repo-id], name, baseurl or mirrorlist, and enabled=1 / gpgcheck=1
  5. Add EPEL Repository: Install Extra Packages for Enterprise Linux with sudo yum install epel-release -y; this unlocks thousands of additional packages not in the base repo
  6. Clean & Rebuild Cache: Run sudo yum clean all to remove cached metadata, then sudo yum makecache to rebuild the local package index from all enabled repos
  7. Update System: Apply all available updates with sudo yum update -y; use sudo yum update <package-name> to update a specific package only
  8. Install & Remove Packages: Install with sudo yum install <package> -y; remove with sudo yum remove <package> -y; use sudo yum reinstall <package> to fix corrupted installs
  9. Search & Info: Search available packages with yum search <keyword>; inspect package details (version, dependencies, size) with yum info <package> before installing
  10. YUM Groups & History: Install predefined software groups with sudo yum groupinstall "Development Tools" -y; review and roll back transactions using yum history list and yum history undo <id>

Install & Configure Nginx

Linux · Web Server
  1. Update Packages: Run sudo apt update && sudo apt upgrade -y (Debian/Ubuntu) or sudo dnf update -y (RHEL/CentOS) to ensure the package list is current
  2. Install Nginx: Run sudo apt install nginx -y (Debian/Ubuntu) or sudo dnf install nginx -y (RHEL/CentOS); verify with nginx -v
  3. Start & Enable Service: Run sudo systemctl start nginx and sudo systemctl enable nginx to start Nginx and persist it across reboots
  4. Configure Firewall: Allow HTTP/HTTPS traffic — sudo ufw allow 'Nginx Full' (UFW) or sudo firewall-cmd --permanent --add-service=http --add-service=https && sudo firewall-cmd --reload (firewalld)
  5. Verify Default Page: Open a browser and navigate to the server's IP (e.g. http://<server-ip>); you should see the default Nginx welcome page
  6. Create Server Block: Create /etc/nginx/sites-available/yourdomain.com with a server block defining listen 80, server_name, and root / index directives
  7. Enable Site: Symlink the config — sudo ln -s /etc/nginx/sites-available/yourdomain.com /etc/nginx/sites-enabled/; test with sudo nginx -t before reloading
  8. Reload Nginx: Apply changes with sudo systemctl reload nginx; use sudo systemctl status nginx to confirm the service is active and running without errors
  9. Configure SSL (Optional): Install Certbot — sudo apt install certbot python3-certbot-nginx -y; obtain a free Let's Encrypt cert with sudo certbot --nginx -d yourdomain.com
  10. Log Monitoring: Check access logs at /var/log/nginx/access.log and error logs at /var/log/nginx/error.log; use sudo tail -f /var/log/nginx/error.log for real-time debugging

AWS

Amazon Web Services infrastructure, EC2, VPC, IAM, and cloud operations

IAM User & Role Management

AWS · Security
  1. Access IAM Console: Log in to AWS Console → search IAM; note that IAM is a global service — changes apply across all regions; never use the root account for daily operations
  2. Create IAM User: IAM → Users → Add Users; set a username, choose credential type (Console password and/or Programmatic access); enable MFA immediately after creation for all human users
  3. Assign Permissions: Attach permissions via managed policies (e.g. AmazonS3ReadOnlyAccess), inline policies, or group membership; always follow the principle of least privilege — grant only what the user needs
  4. Create IAM Groups: IAM → User Groups → Create Group; attach relevant policies to the group; assign users to groups rather than attaching policies directly — simplifies permission management at scale
  5. Create IAM Role: IAM → Roles → Create Role; select trusted entity type (AWS Service, another account, or Web Identity); common use: EC2 role to access S3 without embedding access keys in code
  6. Attach Role to Service: For EC2, go to Instances → Actions → Security → Modify IAM Role; select the role; for Lambda, assign the execution role during function creation or via Configuration → Permissions
  7. Create Custom Policy: IAM → Policies → Create Policy; use the Visual Editor or JSON to define Effect (Allow/Deny), Actions (e.g. s3:GetObject), and Resources (specific ARN or wildcard); version and review before attaching
  8. Enable MFA: IAM → Users → select user → Security Credentials → Assign MFA Device; choose Virtual MFA (Google Authenticator / Authy), hardware token, or U2F key; enforce MFA via SCP or IAM condition keys
  9. Generate Access Keys: IAM → Users → Security Credentials → Create Access Key; download the CSV immediately — secret key is shown only once; rotate keys every 90 days and deactivate unused keys promptly
  10. Audit with IAM Credential Report: IAM → Credential Report → Download; review last-used dates, MFA status, and key age; use IAM Access Analyzer to identify over-permissive policies and external resource access

Create EC2 Instance

AWS · Compute
  1. Sign in to AWS Console: Navigate to console.aws.amazon.com, sign in with your IAM credentials, and ensure you are in the correct region (top-right region selector) before creating the instance — resources are region-specific
  2. Open EC2 Dashboard: Search for EC2 in the services menu → click EC2 → on the Dashboard click Launch Instance; review running instance count and limits before proceeding to avoid hitting service quotas
  3. Name & Tags: Enter a meaningful instance name and add resource tags — at minimum set Name, Environment (dev/staging/prod), Owner, and CostCenter; tags are critical for billing visibility, automation, and governance at scale
  4. Choose Amazon Machine Image (AMI): Select from Quick Start (Amazon Linux 2023, Ubuntu, Windows), My AMIs (custom golden images), or AWS Marketplace; prefer the latest AWS-maintained AMIs for up-to-date security patches and compatibility
  5. Select Instance Type: Choose based on workload requirements — t3.micro/t3.small for dev/test, t3.medium for light production, m6i.large for general-purpose, c6i for compute-heavy, r6i for memory-intensive; use the Compare Instance Types link to evaluate options
  6. Set Up Key Pair: Select an existing key pair or create a new one; download the .pem file and store it securely (chmod 400 on Linux); this is the only authentication method for SSH — loss of the key means loss of direct instance access
  7. Configure Network: Select your VPC and the appropriate subnet (public subnet for internet-accessible instances, private for backend); enable Auto-assign Public IP only for internet-facing instances; select or create a Security Group with least-privilege inbound rules
  8. Configure Storage: Set the root EBS volume size (minimum 20 GB recommended for production); choose gp3 volume type for best price-performance; enable Delete on Termination only for non-persistent data; enable EBS encryption with a KMS key for all sensitive workloads
  9. Advanced Details: Assign an IAM Instance Profile for AWS service access (S3, SSM, CloudWatch); optionally add User Data script for bootstrapping (install packages, configure services at first boot); set Termination Protection to enabled for production instances
  10. Review & Launch: Verify all settings in the Summary panel — AMI, instance type, key pair, VPC, subnet, security group, and storage; click Launch Instance and wait for status checks to show 2/2 passed before connecting or deploying applications

Launch an EC2 Instance

AWS · Compute
  1. Open EC2 Console: Log in to AWS Console → EC2 → Launch Instance; choose a descriptive Name tag — critical for identifying instances in large environments
  2. Select AMI: Choose an Amazon Machine Image — Amazon Linux 2023 for general workloads, Ubuntu 22.04 LTS for dev/web servers, Windows Server 2022 for .NET apps; prefer AWS-maintained AMIs for patched baselines
  3. Choose Instance Type: Select instance family based on workload — t3/t4g (burstable, dev/test), m6i (general purpose), c6i (compute-intensive), r6i (memory-intensive); check vCPU and RAM against your requirements
  4. Configure Key Pair: Create or select an existing key pair (.pem for Linux SSH, .ppk for PuTTY); store the private key securely — AWS does not retain a copy; without it, Linux instance access is lost permanently
  5. Network Settings: Select the VPC and subnet (public for internet-facing, private for internal); enable Auto-assign Public IP for public instances; create or assign a Security Group with required inbound rules (SSH 22, HTTP 80, HTTPS 443)
  6. Configure Storage: Set root EBS volume size (default 8 GB for Amazon Linux — increase to 20-30 GB for production); select gp3 for cost-effective SSD performance; enable encryption using AWS KMS key
  7. Add User Data (Optional): Scroll to Advanced Details → User Data; paste a bootstrap script (e.g. install Nginx on first boot); script runs as root at launch — use for automated software installation and configuration
  8. Assign IAM Role: Under Advanced Details → IAM Instance Profile, attach a role granting the instance access to AWS services (S3, SSM, CloudWatch) without storing credentials on the instance
  9. Launch & Connect: Review summary and click Launch Instance; wait for Instance State to show Running and Status Checks to pass 2/2; connect via EC2 Instance Connect, SSH with key pair, or AWS Systems Manager Session Manager
  10. Post-Launch Validation: Verify connectivity, install updates, confirm attached IAM role permissions, set up CloudWatch agent for metrics and logs, and add Name/Environment/Owner tags for governance

S3 Bucket Setup & Policy Configuration

AWS · Storage
  1. Create S3 Bucket: AWS Console → S3 → Create Bucket; choose a globally unique name (lowercase, hyphens allowed); select the AWS Region closest to your users or application; bucket names cannot be changed after creation
  2. Block Public Access: By default all public access is blocked — keep this enabled for private data; only disable specific settings if hosting a static website or requiring public object access; document any exceptions
  3. Enable Versioning: Bucket Properties → Versioning → Enable; versioning protects against accidental deletion and overwrites; once enabled it can only be suspended, not disabled; combine with lifecycle rules to control storage costs
  4. Enable Encryption: Properties → Default Encryption → Enable; choose SSE-S3 (AWS-managed keys, free) or SSE-KMS (customer-managed keys via AWS KMS, additional cost but audit trail); enforce encryption via bucket policy denying unencrypted uploads
  5. Configure Bucket Policy: Permissions → Bucket Policy → Policy Editor; write JSON policy granting or denying access by Principal (IAM user/role/account), Action (s3:GetObject, s3:PutObject), and Resource (specific bucket ARN or prefix)
  6. Static Website Hosting: Properties → Static Website Hosting → Enable; set index document (index.html) and error document (error.html); disable Block Public Access and add a bucket policy allowing s3:GetObject for all principals
  7. Set Up Lifecycle Rules: Management → Lifecycle Rules → Create; transition objects to S3 Standard-IA after 30 days, Glacier after 90 days, and expire (delete) after 365 days; apply to entire bucket or a specific prefix/tag
  8. Enable Access Logging: Properties → Server Access Logging → Enable; specify a target bucket (separate from source) and prefix; logs capture requester, bucket, request time, action, response status — essential for auditing and troubleshooting
  9. Configure CORS (if needed): Permissions → CORS → Edit; add a JSON rule defining AllowedOrigins, AllowedMethods (GET, PUT), and AllowedHeaders; required when a web app on a different domain reads or writes S3 objects directly
  10. Test & Validate: Upload a test object and verify access using the S3 Console or AWS CLI (aws s3 cp file.txt s3://bucket-name/); confirm bucket policy restrictions with the IAM Policy Simulator before production use

Create & Configure a VPC

AWS · Networking
  1. Plan CIDR Block: Design your IP address space before creating — use a /16 block (e.g. 10.0.0.0/16 = 65,536 IPs) for flexibility; avoid overlapping with on-premises ranges if VPN/Direct Connect is planned; document subnet allocation upfront
  2. Create the VPC: AWS Console → VPC → Your VPCs → Create VPC; enter name tag and IPv4 CIDR block; enable DNS Resolution and DNS Hostnames — required for services like RDS and ECS to resolve correctly
  3. Create Subnets: VPC → Subnets → Create Subnet; create at least one public subnet (e.g. 10.0.1.0/24) and one private subnet (e.g. 10.0.2.0/24) per Availability Zone; distribute across 2-3 AZs for high availability
  4. Create & Attach Internet Gateway: VPC → Internet Gateways → Create IGW → name it and attach to your VPC; one IGW per VPC; the IGW enables outbound internet access for public subnets and inbound access for internet-facing resources
  5. Configure Route Tables: Create a Public Route Table — add a route 0.0.0.0/0 pointing to the IGW and associate public subnets; leave the Private Route Table with local route only; private subnets route internet traffic through a NAT Gateway instead
  6. Deploy NAT Gateway: VPC → NAT Gateways → Create; place it in a public subnet and allocate an Elastic IP; update the private route table with 0.0.0.0/0 pointing to the NAT Gateway; deploy one NAT GW per AZ for high availability
  7. Configure Security Groups: VPC → Security Groups → Create; define inbound rules (e.g. allow HTTPS 443 from 0.0.0.0/0 for web tier, allow 3306 from app-sg for DB tier); security groups are stateful — return traffic is allowed automatically
  8. Configure Network ACLs: VPC → Network ACLs → Edit inbound/outbound rules; NACLs are stateless — you must explicitly allow both inbound and outbound for each flow; use NACLs as a subnet-level firewall for coarse-grained traffic control
  9. Enable VPC Flow Logs: VPC → select VPC → Flow Logs → Create; publish to CloudWatch Logs or S3; capture ACCEPT/REJECT traffic at VPC, subnet, or ENI level; essential for security auditing, troubleshooting, and compliance requirements
  10. Validate Connectivity: Launch test EC2 instances in public and private subnets; verify public instance reaches internet via IGW; verify private instance reaches internet via NAT GW; test inter-subnet communication and confirm Security Group rules behave as expected

Route 53 DNS Management

AWS · Networking
  1. Access Route 53 Console: Log in to AWS Console → search Route 53; note that Route 53 is a global service — hosted zones and records are not region-specific; ensure your IAM user has the AmazonRoute53FullAccess policy attached
  2. Register or Transfer a Domain: Route 53 → Registered Domains → Register Domain; search for your desired domain name, add to cart, and complete registration; for existing domains, choose Transfer Domain and follow the registrar unlock and auth-code process
  3. Create a Hosted Zone: Route 53 → Hosted Zones → Create Hosted Zone; enter your domain name and choose Public (internet-facing) or Private (internal VPC resolution); AWS automatically creates SOA and NS records — note the 4 Name Servers assigned
  4. Update Name Servers: If your domain is registered outside AWS, log in to your registrar (GoDaddy, Namecheap, etc.) and replace the default name servers with the 4 Route 53 NS values; DNS propagation typically takes 24–48 hours globally
  5. Create DNS Records: Inside the Hosted Zone → Create Record; add an A record pointing your root domain to an IP or load balancer, a CNAME for subdomains (e.g. www → yourdomain.com), MX records for email routing, and TXT records for domain verification (SPF, DKIM)
  6. Configure Alias Records: Use Alias records (Route 53-specific) instead of CNAMEs for root domains; Alias records can point directly to AWS resources — Application Load Balancers, CloudFront distributions, S3 static websites, and API Gateway endpoints — with no extra charge for queries
  7. Set Up Routing Policies: Choose a routing policy per record — Simple (default, single value), Weighted (A/B traffic split by percentage), Latency-based (routes to lowest-latency region), Failover (active/passive with health checks), or Geolocation (route by user country/continent)
  8. Configure Health Checks: Route 53 → Health Checks → Create; set protocol (HTTP/HTTPS/TCP), endpoint (IP or domain), path (e.g. /health), and check interval (30s standard, 10s fast); attach health checks to Failover or Weighted records to automatically remove unhealthy endpoints
  9. Enable DNS Query Logging: Hosted Zone → Configure Query Logging → select or create a CloudWatch Log Group; logs capture query name, type, response code, and resolver IP — useful for traffic analysis, debugging resolution failures, and security auditing
  10. Test & Validate: Use the Route 53 Test Record Set tool (Hosted Zone → Test record set) to simulate DNS queries; validate externally with CLI tools — dig yourdomain.com, nslookup yourdomain.com, or host yourdomain.com — and confirm TTL, record values, and routing behaviour are correct

Auto Scaling Group Configuration

AWS · Compute
  1. Prerequisites: Ensure you have a working AMI (or launch template), a VPC with at least 2 subnets across different AZs, and a configured Security Group before creating the ASG
  2. Create a Launch Template: EC2 → Launch Templates → Create; define AMI, instance type, key pair, IAM role, Security Group, and User Data bootstrap script; versioning is supported — always use the latest version in the ASG
  3. Create Auto Scaling Group: EC2 → Auto Scaling Groups → Create; name the ASG, select the Launch Template and version; choose VPC and select multiple subnets across AZs for high availability and fault tolerance
  4. Attach Load Balancer: In the ASG wizard, attach an existing Application Load Balancer target group or create one; enable ELB health checks so the ASG replaces instances that fail load balancer health checks, not just EC2 status checks
  5. Set Capacity Limits: Define Minimum (floor — ASG never scales below this), Maximum (ceiling — ASG never exceeds this), and Desired (current target count) capacity; start with min=2, desired=2, max=6 for a typical production workload
  6. Configure Scaling Policies: Choose Target Tracking (simplest — e.g. keep average CPU at 50%), Step Scaling (scale by fixed increments based on CloudWatch alarm thresholds), or Scheduled Scaling (scale up before known traffic spikes like business hours or events)
  7. Set Cooldown Period: Default cooldown is 300 seconds — prevents the ASG from launching or terminating additional instances before the previous scaling activity takes effect; tune lower (60–120s) for faster-responding workloads
  8. Configure Instance Refresh: ASG → Instance Refresh → Start; set minimum healthy percentage (e.g. 80%) and warm-up time; use this to safely roll out new AMI versions or launch template changes across the fleet without downtime
  9. Enable Lifecycle Hooks: Add Launch and Terminate hooks to run custom actions (install agents, drain connections, back up logs) before an instance is put into service or removed; hooks pause the instance in a Pending:Wait or Terminating:Wait state
  10. Test & Monitor: Manually set desired capacity to trigger a scale-out; verify new instances register with the load balancer and pass health checks; monitor ASG activity history, CloudWatch metrics (GroupDesiredCapacity, GroupInServiceInstances), and SNS notifications for scaling events

CloudWatch Monitoring & Alerts

AWS · Monitoring
  1. Access CloudWatch Console: AWS Console → CloudWatch; CloudWatch is a regional service — switch to the correct region; it collects metrics, logs, events, and traces from virtually all AWS services automatically
  2. Explore Default Metrics: CloudWatch → Metrics → All Metrics; browse namespaces (AWS/EC2, AWS/RDS, AWS/ELB, etc.); key EC2 metrics include CPUUtilization, NetworkIn/Out, DiskReadOps — note that memory and disk usage require the CloudWatch Agent
  3. Install CloudWatch Agent: On EC2, install the agent via Systems Manager (Run Command → AWS-ConfigureAWSPackage → AmazonCloudWatchAgent) or manually; configure with wizard (sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-config-wizard) to collect memory, disk, and custom app metrics
  4. Create a Dashboard: CloudWatch → Dashboards → Create Dashboard; add widgets (Line, Number, Gauge, Bar); pin key metrics like CPU, memory, request count, error rate, and latency across services; share dashboards across accounts using cross-account observability
  5. Create a CloudWatch Alarm: Metrics → select metric → Create Alarm; set the threshold (e.g. CPUUtilization > 80% for 2 consecutive 5-minute periods); define alarm states: OK, ALARM, INSUFFICIENT_DATA; alarms can trigger SNS, Auto Scaling, or EC2 actions
  6. Set Up SNS Notifications: Create an SNS Topic (Simple Notification Service → Create Topic → Standard); add email/SMS/Lambda subscriptions; confirm the email subscription; attach the SNS topic to CloudWatch Alarms to receive immediate alerts on threshold breaches
  7. Configure Log Groups: CloudWatch → Log Groups → Create; applications and AWS services push logs here; set retention period (7, 14, 30, 90 days) to control storage costs; use log groups per application/environment (e.g. /prod/nginx/access, /prod/app/errors)
  8. Create Metric Filters: Log Groups → select group → Metric Filters → Create; define a filter pattern (e.g. ERROR or [status=5*, ...]) to extract numeric metrics from log data; publish the metric to a custom namespace and set it as the basis for an alarm
  9. Set Up CloudWatch Synthetics: CloudWatch → Synthetics → Create Canary; write or use a blueprint script to simulate user journeys (check URL availability, API responses, login flows); canaries run on a schedule and alarm when endpoints fail or latency exceeds thresholds
  10. Enable CloudWatch Container Insights: For ECS/EKS workloads, enable Container Insights in cluster settings; it provides CPU, memory, network, and storage metrics per task/pod; use Contributor Insights to identify top-N contributors to high traffic or error rates in logs and metrics

Elastic Load Balancer Setup

AWS · Networking
  1. Choose Load Balancer Type: Application Load Balancer (ALB) for HTTP/HTTPS and path/host-based routing; Network Load Balancer (NLB) for TCP/UDP with ultra-low latency and static IPs; Gateway Load Balancer (GWLB) for inline network appliances like firewalls
  2. Create the Load Balancer: EC2 → Load Balancers → Create; select ALB; enter a name, choose Internet-facing (public) or Internal (private VPC); select at least 2 Availability Zones and their public subnets for high availability
  3. Configure Security Groups: Create or assign a Security Group to the ALB allowing inbound HTTP (80) and HTTPS (443) from 0.0.0.0/0; EC2 instance Security Groups should allow traffic only from the ALB Security Group — never expose instance ports directly to the internet
  4. Create a Target Group: EC2 → Target Groups → Create; choose target type (Instances, IP addresses, or Lambda); set protocol (HTTP), port (e.g. 80), and VPC; configure health check path (e.g. /health), healthy threshold (2), unhealthy threshold (3), and interval (30s)
  5. Register Targets: Select EC2 instances or IPs to add to the target group; set the port each target receives traffic on; newly registered targets enter an Initial state and become Healthy after passing the configured number of consecutive health checks
  6. Configure Listeners & Rules: ALB → Listeners → Add Listener; HTTP:80 — add a redirect rule to HTTPS:443; HTTPS:443 — add forward rule to your target group; add path-based rules (e.g. /api/* → API target group, /* → web target group) for microservice routing
  7. Attach SSL Certificate: HTTPS listener → select certificate from AWS Certificate Manager (ACM); request a free public certificate in ACM by validating domain ownership via DNS (add CNAME record) or email; ACM auto-renews certificates before expiry
  8. Enable Sticky Sessions (if needed): Target Group → Attributes → Stickiness → Enable; choose Load Balancer-generated cookie (AWSALB) or Application cookie; set duration; use only for stateful apps — stateless architectures with shared session stores (Redis/DynamoDB) are preferred
  9. Enable Access Logs: Load Balancer → Attributes → Access Logs → Enable; specify an S3 bucket with the correct bucket policy; logs capture client IP, request time, target, response codes, and latency — essential for troubleshooting and security analysis
  10. Test & Monitor: Copy the ALB DNS name and test in a browser or with curl; verify requests are distributed across targets; monitor CloudWatch metrics — RequestCount, TargetResponseTime, HTTPCode_ELB_5XX_Count, HealthyHostCount — and set alarms on unhealthy host count and 5xx errors

RDS Database Setup

AWS · Database
  1. Choose Database Engine: AWS Console → RDS → Create Database; select engine — MySQL, PostgreSQL (most popular open-source options), MariaDB, Oracle, SQL Server, or Amazon Aurora (MySQL/PostgreSQL-compatible with up to 5x performance improvement)
  2. Select Deployment Option: Choose Standard Create for full control; select Multi-AZ DB Instance for production (synchronous standby replica in a second AZ for automatic failover); use Single-AZ only for dev/test to reduce costs
  3. Configure Instance Class: Select DB instance class — db.t3.micro (free tier, dev/test), db.t3.medium (light production), db.m6i.large (general production), db.r6i.large (memory-intensive); match vCPU and RAM to your query load and connection count
  4. Set Storage: Choose General Purpose SSD (gp3) for most workloads; set allocated storage (minimum 20 GB); enable Storage Autoscaling with a maximum threshold to prevent out-of-space errors during unexpected growth; enable encryption at rest using AWS KMS
  5. Configure Connectivity: Select VPC and subnet group (create a DB Subnet Group with subnets in at least 2 AZs); set Public Accessibility to No for production; create or assign a VPC Security Group allowing inbound on the DB port (3306 MySQL, 5432 PostgreSQL) only from app-tier Security Groups
  6. Set Credentials: Enter a master username and a strong master password (or let AWS manage it via Secrets Manager — recommended); store credentials in AWS Secrets Manager for automatic rotation and secure retrieval by applications without hardcoding passwords
  7. Configure Backups: Set automated backup retention period (7–35 days); choose a backup window during low-traffic hours; enable point-in-time recovery (PITR) allowing restore to any second within the retention window; create manual snapshots before major changes
  8. Enable Enhanced Monitoring & Logs: Enable Enhanced Monitoring (1–60 second granularity for OS metrics); enable CloudWatch Logs export (error log, slow query log, general log); set slow query threshold to identify and optimise poorly performing queries
  9. Create Read Replicas (if needed): RDS → select DB → Actions → Create Read Replica; read replicas offload SELECT queries from the primary, improving read throughput; promote a read replica to standalone if you need to scale writes or recover from a regional failure
  10. Connect & Validate: Use the RDS endpoint (found in Connectivity tab) to connect from an EC2 instance in the same VPC — test with mysql -h endpoint -u admin -p or psql -h endpoint -U admin; verify Security Group rules, subnet routing, and parameter group settings if connection fails

CloudFront CDN Configuration

AWS · Networking
  1. Understand CloudFront: CloudFront is AWS's global CDN with 400+ edge locations worldwide; it caches content close to users to reduce latency, offloads origin traffic, provides DDoS protection via AWS Shield Standard, and integrates natively with S3, ALB, API Gateway, and custom HTTP origins
  2. Create a Distribution: AWS Console → CloudFront → Create Distribution; CloudFront has two delivery methods — Web (HTTP/HTTPS for websites and APIs) and RTMP (deprecated, for streaming); select Web for all modern use cases
  3. Configure Origin: Set the Origin Domain — S3 bucket URL for static sites (use the REST endpoint, not the website endpoint), ALB DNS name for dynamic apps, or a custom HTTP server; for S3, enable Origin Access Control (OAC) to restrict bucket access exclusively to CloudFront — never expose the bucket publicly
  4. Set Default Cache Behaviour: Define the Viewer Protocol Policy (Redirect HTTP to HTTPS — always enable); set Allowed HTTP Methods (GET/HEAD for static content, GET/HEAD/POST/PUT/DELETE for APIs); configure Cache Policy (CachingOptimized for static, CachingDisabled for dynamic/API content)
  5. Configure Cache Settings: Use managed cache policies (CachingOptimized sets TTL 1 day to 1 year) or create a custom policy; set minimum, default, and maximum TTL; use Cache-Control headers from your origin to control per-object TTL; configure origin request policies to forward headers, cookies, and query strings selectively
  6. Add Custom Domain & SSL: Distribution Settings → Alternate Domain Names (CNAMEs) → add your domain (e.g. cdn.yourdomain.com); select Custom SSL Certificate from ACM — the certificate must be in us-east-1 (N. Virginia) regardless of your distribution's region; create a CNAME record in Route 53 pointing to the CloudFront distribution domain
  7. Enable Compression: Cache Behaviour → Compress Objects Automatically → Yes; CloudFront automatically compresses text-based files (HTML, CSS, JS, JSON) with Gzip and Brotli if the viewer supports it; reduces transfer size by 60–80% improving load times and reducing data transfer costs
  8. Set Up WAF Integration: Associate an AWS WAF Web ACL with the distribution to block common web exploits (SQL injection, XSS, bad bots); use AWS Managed Rules for instant protection; WAF rules are evaluated at edge locations before requests reach your origin
  9. Configure Geo-Restriction: Distribution → Security → Geo-Restriction → Edit; create an allowlist (only specified countries can access) or blocklist (deny specific countries); useful for licensing compliance, regulatory requirements, or blocking known high-risk regions
  10. Invalidate Cache & Monitor: After deploying new content, create an invalidation (Invalidations → Create → path /* or specific files) to purge cached objects from all edge locations; monitor with CloudWatch metrics — Requests, BytesDownloaded, 4xxErrorRate, 5xxErrorRate, CacheHitRate — and enable CloudFront access logs to S3 for detailed analysis
