Standard Operating Procedures

Detailed step-by-step procedures for VMware administration, Windows Server management, and cloud infrastructure tasks — built from real enterprise experience.

VMware

vSphere, NSX, vSAN, Horizon, and lifecycle management procedures

ESXi Host Deployment

VMware · Infrastructure
  1. Hardware Prerequisites: Verify server is on the VMware Hardware Compatibility List (HCL). Confirm CPU supports hardware virtualisation (Intel VT-x or AMD-V) and BIOS virtualisation extensions are enabled. Check minimum requirements: 64-bit x86 CPU, 4 GB RAM (32 GB+ recommended for production), at least two NICs, and local storage for ESXi boot (USB, SD, or dedicated SSD).
  2. Download ESXi ISO: Log in to the VMware Customer Connect portal and download the correct ESXi version ISO (custom OEM ISO if using vendor-specific drivers for Dell, HP, Cisco, etc.). Verify the SHA256 checksum of the downloaded ISO before creating boot media.
  3. Prepare Boot Media: Mount the ESXi ISO via iDRAC (Dell), iLO (HPE), or CIMC (Cisco) virtual media console. Alternatively, write the ISO to a USB drive using Rufus or dd. Set the server BIOS boot order to boot from the chosen media first.
  4. Run ESXi Installer: Boot the server. The ESXi installer loads — accept the EULA, select the target disk for ESXi installation (dedicated boot LUN or local disk — not the same disk used for VM storage). Choose the keyboard layout and set a strong root password meeting your organisation's complexity policy.
  5. Configure Management Network via DCUI: After installation and reboot, press F2 at the DCUI screen and log in as root. Navigate to Configure Management Network. Select the correct physical NIC (vmnic) for management, set the VLAN ID if required, configure a static IP address, subnet mask, default gateway, and DNS servers. Press Escape and confirm the network restart.
  6. Verify Network Connectivity: From DCUI, run Test Management Network — ping the default gateway, DNS servers, and a known reachable host. Confirm all tests pass. If any test fails, recheck the NIC selection, VLAN tagging, and IP configuration before proceeding.
  7. Enable SSH & ESXi Shell: In DCUI → Troubleshooting Options → Enable SSH and Enable ESXi Shell. These are required for remote CLI management. Note: For production environments, enable SSH only during maintenance and disable afterwards per security policy. SSH can also be enabled persistently via vCenter Host Profile.
  8. Configure NTP: SSH into the host (ssh root@<ESXi-IP>) and run: esxcli system ntp set --server=<NTP-IP1> --server=<NTP-IP2> then esxcli system ntp set --enabled=true. Alternatively, configure NTP from vSphere Client → Host → Configure → Time Configuration. Confirm time sync is active: esxcli system ntp get.
  9. Configure DNS & Hostname: Verify the host FQDN is correctly set: esxcli system hostname set --fqdn=esxi01.corp.local. Confirm DNS resolution works both forward and reverse: nslookup esxi01.corp.local and nslookup <ESXi-IP>. Incorrect DNS will cause vCenter certificate and HA issues later.
  10. Configure Syslog: Forward ESXi logs to a central syslog server for auditing. Run: esxcli system syslog config set --loghost=udp://<syslog-IP>:514 then esxcli system syslog reload. Open the required firewall rule: esxcli network firewall ruleset set --enabled=true --ruleset-id=syslog.
  11. Apply Security Hardening: Set the host acceptance level to restrict unsigned VIBs: esxcli software acceptance set --level=PartnerSupported. Disable unused services (CIM, SNMP if not needed). Enable lockdown mode after adding to vCenter to prevent direct host access. Configure shell timeout: esxcli system settings advanced set -o /UserVars/ESXiShellInteractiveTimeOut -i 900.
  12. Configure VMkernel Adapters: Create VMkernel ports for management, vMotion, vSAN (if applicable), and Fault Tolerance logging. Each VMkernel should be on the appropriate VLAN and have its traffic type enabled. vMotion VMkernel should have at least 10 GbE and Jumbo Frames (MTU 9000) enabled if using 10 GbE infrastructure.
  13. Add Host to vCenter: In vSphere Client, right-click the target datacenter or cluster → Add Host. Enter the ESXi host IP/FQDN and root credentials. Accept the thumbprint/certificate. Assign the host to the appropriate datacenter, cluster, or standalone host location. vCenter will push the host profile and distributed switch configuration if templates are pre-configured.
  14. Apply Host Profile (if used): If the organisation uses vCenter Host Profiles, attach the standard Host Profile to the newly added host. Run Check Compliance and remediate any non-compliant items (NTP, syslog, security settings, networking). This ensures all hosts in the environment maintain a consistent, policy-driven configuration.
  15. Configure Storage Connectivity: Add the host to storage arrays — zone the host's HBA WWNs in Fibre Channel zoning, or configure iSCSI software initiator with the storage IP and IQN. Rescan HBAs/iSCSI adapters and confirm datastores are visible. For NFS, add the NFS datastore via Datastores → New Datastore → NFS.
  16. Install VMware Tools on Template VMs: Ensure any VM templates stored on the host's datastores have the latest VMware Tools installed, matching the new ESXi version. Outdated VMware Tools can cause compatibility warnings and reduce VM performance management capabilities.
  17. Validate Host in vCenter: Confirm the host appears in vCenter with a green status. Check the Summary tab for any configuration issues (warnings). Verify that vMotion, HA heartbeat, and vSAN (if enabled) are all functional by reviewing the cluster health in vCenter → Cluster → Monitor → vSphere HA.
  18. Run Post-Deployment Checklist: Confirm: host is in the correct cluster, all VMkernel adapters are configured, NTP and DNS are active, syslog is forwarding, firewall rules are correct, SSH is disabled (if policy requires), and host is not in maintenance mode. Document the host IP, FQDN, hardware model, ESXi version, and installation date in the CMDB.

vCenter Server Appliance Deployment

VMware · Management
  1. Prerequisites: Confirm the target ESXi host is reachable, has sufficient resources (minimum 2 vCPU, 12 GB RAM, 415 GB storage for small deployment), and is on a supported version. Prepare a static IP, FQDN, and DNS A/PTR records for the vCSA before starting. Ensure the deploying workstation has network access to the ESXi host on port 443.
  2. Mount vCSA ISO: Download the VMware vCenter Server Appliance ISO from the VMware portal. Mount the ISO on the deployment workstation. Navigate to the vcsa-ui-installer folder and launch the installer for your OS (Windows: installer.exe, Linux: installer, macOS: Installer.app).
  3. Stage 1 — Select Deployment Type: In the installer UI, click Install. Accept the EULA. On the deployment type screen, choose: Embedded Platform Services Controller (recommended for most deployments) or External PSC (for large multi-site vCenter deployments). Click Next.
  4. Stage 1 — Connect to Target ESXi Host: Enter the FQDN or IP of the ESXi host where the vCSA VM will be deployed. Provide root credentials. Accept the host's SSL certificate thumbprint. Specify the vCSA VM name and set a root password for the appliance itself.
  5. Stage 1 — Select Deployment Size: Choose the appropriate deployment size based on inventory scale — Tiny (up to 10 hosts, 100 VMs), Small (100 hosts, 1,000 VMs), Medium (400 hosts, 4,000 VMs), Large (1,000 hosts, 10,000 VMs), X-Large (2,000 hosts, 35,000 VMs). Each size has predefined vCPU, memory, and storage requirements.
  6. Stage 1 — Select Datastore: Choose the datastore on the target ESXi host for the vCSA VM. Enable Enable Thin Disk Mode to save storage space (recommended unless thick provisioning is required by policy). Ensure the selected datastore has sufficient free space for the chosen deployment size.
  7. Stage 1 — Configure Network: Select the port group for the vCSA management network. Choose Static IP allocation. Enter: IP address, subnet prefix/mask, default gateway, DNS servers (primary and secondary), and the fully qualified domain name (FQDN) of the vCSA. The FQDN must resolve in DNS before completing Stage 2.
  8. Stage 1 — Review & Deploy: Review the Stage 1 summary. Confirm all settings are correct — especially the FQDN and IP. Click Finish to begin the VM deployment. The installer will create the vCSA VM, copy the appliance OVA, configure the virtual hardware, and power it on. Stage 1 typically takes 10–20 minutes.
  9. Stage 2 — Begin Appliance Setup: Once Stage 1 completes, click Continue to proceed to Stage 2 (appliance configuration). If the installer closes, access Stage 2 directly by browsing to https://<vCSA-IP>:5480 and clicking the Setup button. Stage 2 configures the internal services and SSO.
  10. Stage 2 — Configure NTP & SSH: Set the NTP server(s) for appliance time synchronisation. Enable SSH access if required for post-deployment administration (can be enabled/disabled later from VAMI at port 5480). Accurate NTP configuration is critical — vCenter and ESXi hosts must be within 5 minutes of each other to prevent authentication failures.
  11. Stage 2 — Configure SSO: Choose Create a new SSO domain for a new environment (enter SSO domain name, typically vsphere.local, and the SSO admin password) or Join existing SSO domain if adding a second vCenter to an existing SSO federation. Record the SSO administrator password securely — it cannot be easily recovered if lost.
  12. Stage 2 — CEIP: Choose whether to join the VMware Customer Experience Improvement Program (CEIP). This is optional and can be changed post-deployment. Click Next to proceed to the final review.
  13. Stage 2 — Review & Finish: Review the Stage 2 configuration summary. Click Finish. Stage 2 initialises all vCenter services (inventory, authentication, licensing, etc.). This typically takes 15–30 minutes. Do not interrupt the process. A progress bar tracks each service initialisation phase.
  14. Access vSphere Client: Once Stage 2 completes, open a browser and navigate to https://<vCSA-FQDN-or-IP>/ui. Log in with administrator@vsphere.local and the SSO password set in Stage 2. Accept the certificate warning (or install a CA-signed certificate via VAMI post-deployment).
  15. Apply vCenter Licence: In vSphere Client → Administration → Licensing → Licences → Add. Enter the vCenter Server licence key. Assign the licence to the vCenter Server asset. Verify the licence type and expiry are correct. Unlicensed vCenter operates in evaluation mode (60 days) with full functionality but will expire.
  16. Create Datacenter & Cluster: In the Hosts and Clusters view, right-click the vCenter root → New Datacenter. Give the datacenter a logical name (e.g., DC-LON-01). Right-click the datacenter → New Cluster. Name the cluster and enable vSphere HA and DRS as required. This prepares the logical container before adding ESXi hosts.
  17. Configure vCenter Identity Sources: Navigate to Administration → Single Sign On → Configuration → Identity Source. Add Active Directory (Integrated Windows Authentication or LDAP) as an identity source. This allows AD users and groups to authenticate to vSphere Client. Assign vCenter roles (Administrator, ReadOnly) to AD groups via Administration → Access Control → Global Permissions.
  18. Configure SMTP for Alarms: In vSphere Client → Administration → vCenter Server Settings → Mail, enter the SMTP server address and sender email address. Configure vCenter alarm actions to send email notifications for critical events (host disconnected, VM power-off, datastore low space) to the infrastructure team distribution list.
  19. Replace Self-Signed Certificate (Recommended): By default, vCSA uses a self-signed certificate. For production environments, replace it with a CA-signed certificate via VAMI (https://<vCSA-IP>:5480) → Certificate Management → Machine Certificate → Replace. Use an internal CA or public CA certificate with the vCSA FQDN as the Common Name and Subject Alternative Name.
  20. Validate & Document: Confirm vCenter is accessible, licenced, and connected to its first ESXi host (add a host to verify end-to-end functionality). Run a test vMotion to validate the environment. Document the vCSA IP, FQDN, SSO domain, admin credentials (in the vault), deployment size, vCenter version, and datastore location in the CMDB and infrastructure runbook.

HA/DRS Cluster Setup

VMware · High Availability
  1. Prerequisites: Confirm all ESXi hosts are added to vCenter, running the same ESXi version (mixed versions are supported but not recommended), connected to shared storage (FC, iSCSI, NFS, or vSAN), and have vMotion VMkernel adapters configured on a dedicated network with at least 1 GbE (10 GbE recommended).
  2. Create the Cluster: In vSphere Client → Hosts and Clusters, right-click the target Datacenter → New Cluster. Enter a meaningful cluster name (e.g., CL-PROD-01). Check the boxes to enable vSphere DRS and vSphere HA at creation time, or configure them post-creation. Click OK — the cluster container is created immediately.
  3. Add Hosts to the Cluster: Right-click the cluster → Add Hosts. Add ESXi hosts by entering their IPs/FQDNs and root credentials, or drag existing standalone hosts from the datacenter into the cluster. vCenter will validate each host's configuration and push cluster settings. Review any configuration issues flagged during the add process.
  4. Configure vSphere HA — Enable & Admission Control: Select the cluster → Configure → vSphere Availability → Edit. Enable HA. Set the Admission Control policy — choose one of: Cluster resource percentage (e.g., reserve 25% CPU and memory for failover), Slot policy (legacy method based on slot sizes), or Dedicated failover hosts (specific hosts reserved for failover only). The resource percentage method is most commonly used in modern deployments.
  5. Configure HA — Host Monitoring & Failure Response: Under HA settings, enable Host Monitoring. Set the response for Host Failure: Restart VMs (recommended). Set the VM restart priority levels — Critical VMs (Domain Controllers, management VMs) should be High; standard workloads Medium; test VMs Low. Configure the restart order with dependencies if required (e.g., DB before App before Web tier).
  6. Configure HA — VM Monitoring: Enable VM Monitoring under HA to restart individual VMs that stop sending VMware Tools heartbeats (not just host failures). Set sensitivity to Medium for production VMs. Configure per-VM overrides for stateful apps (databases) that may have intentional long pauses — set their monitoring sensitivity to Disabled or Low to avoid false restarts.
  7. Configure HA — Heartbeat Datastores: vSphere HA uses datastore heartbeating as a secondary isolation check (in addition to the management network). Under HA → Heartbeat Datastores, select at least two datastores accessible to all hosts in the cluster. This prevents split-brain scenarios when the management network fails but hosts are still running.
  8. Configure HA — Isolation Response: Set the Host Isolation Response — what happens if a host loses management network connectivity but VMs are still running: Power off and restart VMs (most aggressive), Shut down and restart VMs (graceful, requires VMware Tools), or Disabled (VMs stay running on the isolated host). For most production environments, Shut down and restart VMs is recommended.
  9. Configure vSphere DRS — Automation Level: Select the cluster → Configure → vSphere DRS → Edit. Enable DRS and set the automation level: Manual (DRS recommends but you approve all migrations), Partially Automated (automatic initial placement, manual ongoing), or Fully Automated (DRS migrates VMs automatically for load balancing). Set the migration threshold — a more aggressive threshold results in more frequent migrations.
  10. Configure DRS — Resource Pools & Shares: Create Resource Pools within the cluster to assign CPU and memory entitlements to groups of VMs. Right-click cluster → New Resource Pool. Assign Shares (High/Normal/Low) and Reservations (guaranteed minimums) per pool. Example: a Production pool with High shares and a Dev pool with Low shares ensures production VMs win resource contention.
  11. Configure DRS — VM/Host Affinity & Anti-Affinity Rules: Create affinity rules under Cluster → Configure → VM/Host Rules → Add. Use Keep Virtual Machines Together (affinity) to ensure related VMs (e.g., a web and caching VM) stay on the same host for low latency. Use Separate Virtual Machines (anti-affinity) to ensure HA pairs (e.g., two AD domain controllers) run on different hosts for resilience.
  12. Configure vSphere DRS — Proactive HA (if supported): If hardware health providers are available (Dell OpenManage, HPE OneView), enable Proactive HA. This allows DRS to pre-emptively migrate VMs away from hosts with degraded hardware (failing PSU, fan, disk) before they cause a full failure. Enable under Cluster → Configure → Proactive HA.
  13. Configure EVC Mode: Enable Enhanced vMotion Compatibility (EVC) if the cluster contains hosts with different CPU generations. Select the EVC baseline CPU level (e.g., Intel Skylake) — all hosts must support the selected baseline. EVC ensures live vMotion migrations succeed across CPU generations by masking advanced CPU features to the lowest common denominator.
  14. Validate HA — Simulate Host Failure: To test HA, place a non-critical ESXi host into Maintenance Mode (this triggers VM restarts via HA as if the host failed, if you first disable DRS migration). Alternatively, in a lab environment, disconnect the host from the management network and confirm VMs restart on remaining hosts within the HA restart timer window.
  15. Validate DRS — Load Balancing: Check DRS recommendations in Cluster → Monitor → DRS. Confirm DRS is generating migration recommendations or executing automatic migrations when hosts are imbalanced. Review the DRS score (100 = fully balanced). If DRS is not triggering, check that all hosts have vMotion configured and that no affinity rules are blocking migrations.
  16. Set Per-VM HA/DRS Overrides: For VMs that need non-default HA or DRS behaviour, configure VM overrides: Cluster → Configure → VM Overrides → Add. Examples: set a critical database VM to HA Restart Priority: Highest and VM Monitoring: Disabled; set a test VM to DRS Automation: Manual to prevent unexpected migrations during testing.
  17. Review Cluster Health & Alarms: After configuration, check Cluster → Monitor → vSphere HA for any configuration errors or warnings (e.g., hosts with no vMotion VMkernel, insufficient failover capacity, datastore heartbeat issues). Resolve all red or yellow warnings before declaring the cluster production-ready. Set vCenter alarms to notify the team if HA admission control is violated.
  18. Document & Baseline: Record the cluster configuration: cluster name, HA admission control policy and percentages, DRS automation level and threshold, EVC level, resource pool hierarchy, affinity rules, and per-VM overrides. Save a vSphere configuration export as a baseline. Update the CMDB with the cluster details and notify the operations team of the completed setup.

Distributed Switch Configuration

VMware · Networking
  1. Prerequisites: Confirm vCenter is available (vDS is a vCenter construct — not available with standalone ESXi). Verify all hosts have at least two physical NICs (vmnic) available for vDS uplinks. Plan VLAN IDs, port group names, teaming policy, and MTU settings before starting. vDS requires vSphere Enterprise Plus licence or vSAN/NSX licence on the hosts.
  2. Create the Distributed Switch: In vSphere Client → Networking → Right-click the Datacenter → Distributed Switch → New Distributed Switch. Enter the vDS name (e.g., vDS-Prod-01). Select the vDS version matching your ESXi host version (or lower for backward compatibility). Set the number of uplink ports (typically 2 or 4, matching the number of physical NICs per host dedicated to this vDS).
  3. Configure vDS Settings: Set the default port group name (or delete it and create custom port groups). Configure the MTU — set 9000 for jumbo frames if the physical network supports it (required for vSAN, iSCSI, and high-performance workloads). Enable Network I/O Control (NIOC) to allow bandwidth reservation per traffic type (vMotion, VM, management). Enable Discovery Protocol (CDP or LLDP) for physical switch visibility.
  4. Add Hosts to the vDS: Right-click the vDS → Add and Manage Hosts → Add Hosts. Select all ESXi hosts to add. For each host, assign physical adapters (vmnics) to the vDS uplinks. Ensure the physical NICs assigned to the vDS are not currently used as the sole uplinks for the management network — add them carefully to avoid dropping management connectivity during migration.
  5. Migrate Management VMkernel to vDS: When moving the management VMkernel (vmk0) from a Standard Switch (vSS) to the vDS, migrate it carefully. In the Add/Manage Hosts wizard, assign the VMkernel adapter to the vDS management port group. Verify the management IP remains reachable after migration before removing the old vSS uplinks. Perform this one host at a time.
  6. Create Distributed Port Groups (Management): Right-click the vDS → Distributed Port Group → New Distributed Port Group. Create a port group for management traffic: name it descriptively (e.g., DPG-MGMT-VLAN10), set VLAN type to VLAN, enter the VLAN ID (e.g., 10). Set port binding to Static Binding. Set port allocation to Elastic for dynamic port count scaling.
  7. Create Distributed Port Groups (vMotion): Create a dedicated port group for vMotion traffic: DPG-vMotion-VLAN20, VLAN ID 20. After creation, edit the port group and override the teaming policy to use specific uplinks for vMotion (e.g., Active: uplink2, Standby: uplink1) to ensure vMotion traffic uses dedicated bandwidth and doesn't compete with VM traffic.
  8. Create Distributed Port Groups (VM Networks): Create port groups for VM production traffic: e.g., DPG-VM-PROD-VLAN100 (VLAN 100), DPG-VM-DMZ-VLAN200 (VLAN 200), DPG-VM-DEV-VLAN300 (VLAN 300). For trunk port groups that pass multiple VLANs to a VM (e.g., a virtual firewall), set the VLAN type to VLAN Trunking and specify the VLAN range.
  9. Configure Teaming & Failover Policy: Edit each port group → Teaming and Failover (override from vDS default if needed). Choose the load balancing algorithm: Route based on originating virtual port (default, no physical switch config needed), Route based on IP hash (requires LACP/EtherChannel on the physical switch), or Route based on physical NIC load (dynamic load balancing, requires Enterprise Plus). Set active/standby uplinks per port group traffic class.
  10. Configure LACP (if required): For link aggregation, right-click vDS → Settings → LACP → New LAG. Define the LAG with the required number of ports and the LACP mode (Active or Passive). Assign physical NICs to the LAG per host via the Manage Hosts wizard. Configure matching LACP port-channel on the physical upstream switch. Set the vDS port group teaming policy to use the LAG as the active uplink.
  11. Configure Network I/O Control (NIOC): If NIOC is enabled, configure bandwidth allocations under the vDS → Resource Management. Set shares and reservations per traffic type: Management (50 shares), vMotion (50 shares), vSAN (100 shares — high priority), VM traffic (100 shares). This ensures vSAN and vMotion traffic is not starved during periods of high VM network utilisation.
  12. Configure Port Group Security Policies: Edit each port group → Security. For standard VM port groups: Promiscuous Mode: Reject, MAC Address Changes: Reject, Forged Transmits: Reject. For port groups hosting virtual appliances acting as L2 bridges or network monitors (e.g., NSX Edge, IDS sensors), Promiscuous Mode: Accept may be required. Document any exceptions.
  13. Configure Private VLANs (if required): For environments requiring intra-VLAN isolation (e.g., hosting environments, PCI-DSS zones), configure PVLANs on the vDS. Edit the vDS → Settings → Private VLAN. Define the primary PVLAN ID and secondary PVLAN IDs (Isolated or Community). Assign the secondary PVLAN to port groups. Ensure matching PVLAN configuration on the upstream physical switch.
  14. Migrate Remaining VMkernels: Move vMotion, iSCSI, vSAN, and FT logging VMkernel adapters from the old Standard Switch to the new vDS port groups using the Add/Manage Hosts wizard. Validate each VMkernel is tagged for the correct traffic type (vMotion, vSAN, iSCSI, Management) after migration. Check esxcli network ip interface list via SSH to confirm.
  15. Remove Old Standard Switch: Once all VMkernel adapters and VM port groups are migrated to the vDS, remove any unused physical NICs from the old Standard Switch. If the Standard Switch has no adapters or port groups in use, delete it from the host: Host → Configure → Networking → Virtual Switches → Remove. Do this only after confirming no VMs or VMkernels remain on the vSS.
  16. Validate Connectivity: After migrating all hosts, test: management access (ping each host's management IP), vMotion (perform a live migration between two hosts), VM network (ping from VMs on each port group to confirm VLAN routing and uplink connectivity). Check for any vSphere alarms related to network configuration or uplink failures.
  17. Export vDS Configuration Backup: Right-click the vDS → Settings → Export Configuration. Save the vDS configuration file (.zip) as a backup. This file can be used to restore the entire vDS configuration (port groups, policies, NIOC settings) if the vCenter database is lost or the vDS is accidentally misconfigured. Store the backup in a secure, version-controlled location.
  18. Document & Update CMDB: Record the vDS name, version, uplink count, all port group names and VLAN IDs, teaming policies, NIOC settings, PVLAN configuration (if used), and all host assignments. Include a network diagram showing the physical NIC-to-vDS uplink mapping. Update the CMDB and notify the network team of all VLAN-to-port-group mappings for physical switch documentation alignment.

vSphere Lifecycle Manager (vLCM)

VMware · Patching
  1. Prerequisites: Confirm vCenter Server 7.0 or later (vLCM replaces Update Manager in vSphere 7.0). Ensure the vCenter appliance has internet access to the VMware depot (or configure an internal UMDS/depot proxy if air-gapped). Verify the cluster uses ESXi 7.0+ hosts — vLCM image-based management requires ESXi 7.0 minimum. vLCM is not compatible with clusters still using legacy Update Manager baselines; migrating to images requires conversion.
  2. Understand vLCM Modes: vLCM supports two models: Baselines (legacy, patch-level control, compatible with ESXi 6.x and 7.x) and Single Image (new in 7.0, defines the full desired ESXi stack including base image, components, and firmware add-ons). Use Image mode for new clusters and greenfield deployments; use Baselines for existing environments not yet ready for image conversion. This SOP covers Image mode.
  3. Enable vLCM for the Cluster: In vSphere Client, select the target cluster → Updates tab → Hosts → Image → Manage with a single image. If the cluster currently uses Baselines, you will be prompted to convert. The conversion wizard checks compatibility and migrates existing patch state. Click Enable to proceed. This action is per-cluster and irreversible (cannot revert to Baselines without a cluster rebuild).
  4. Configure the Depot Source: In vCenter → Administration → vSphere Lifecycle Manager → Settings → Patch Download Settings. If connected to the internet, select Use the default VMware depot. For air-gapped environments, configure an Internal HTTP Server running UMDS (vSphere Update Manager Download Service) that mirrors the VMware depot locally. Sync the depot and verify it is reachable.
  5. Define the Desired Image: In the cluster's Updates → Image → Edit Image. Select the ESXi base image version (e.g., ESXi 8.0 Update 2). Add required components: vendor add-ons (Dell, HPE, Cisco custom ISOs with OEM drivers and firmware), additional VIBs (drivers, agents), and firmware add-ons if hardware firmware management via vLCM is desired. The image defines the complete desired software state of every host in the cluster.
  6. Add Hardware Support Manager (Firmware, if applicable): If managing hardware firmware through vLCM (supported with Dell OpenManage, HPE OneView, Lenovo XClarity), register the Hardware Support Manager plugin under vCenter → Administration → vLCM → Hardware Support. Once registered, firmware packages appear as selectable components within the Image definition. This enables full stack management (OS + firmware) from a single vLCM image.
  7. Validate Image Compatibility: Click Validate in the Image editor. vLCM checks the image against the VMware Hardware Compatibility Guide (HCG) for the hosts in the cluster. Any incompatible drivers, conflicting VIBs, or unsupported hardware combinations are flagged. Resolve all WARN and ERROR items before saving the image — common issues include deprecated VIBs, missing driver versions for specific NIC/HBA models, or ABI incompatibilities.
  8. Save the Image: After validation passes (or warnings are reviewed and accepted), click Save. The image is now the desired state for all hosts in the cluster. vLCM will immediately begin a compliance check against all hosts in the cluster to determine which are compliant (already running the defined image) and which are non-compliant (require remediation).
  9. Review Compliance Status: In the cluster Updates tab → Hosts → Compliance, review each host's status: Compliant (up to date), Non-compliant (updates available), or Incompatible (hardware or software conflicts prevent the image from being applied). Click on a non-compliant host to see the specific differences — packages to add, update, or remove — compared to the desired image.
  10. Pre-Remediation Checks: Before starting remediation, verify: HA admission control will not be violated during host maintenance (cluster has enough capacity to absorb VMs from one host at a time), DRS is set to Fully Automated (to evacuate VMs automatically), all VMs on the first host to be patched are not pinned by hard affinity rules, and no active vMotion or storage migrations are running.
  11. Take VM Snapshots / Backups: Snapshot or verify backups of all critical VMs prior to patching. Although ESXi patching via vLCM is non-destructive, having a recovery point is required by most change management policies. Confirm backup completion timestamps are recent enough to meet your RPO requirements.
  12. Schedule Remediation: Click Remediate All (or select specific hosts for staged rollout). In the remediation wizard, choose Immediate or schedule for a specific maintenance window. Configure the remediation options: enable Disable High Availability admission control for the duration of the remediation if needed; set the maintenance mode evacuation timeout; choose whether to retry failed remediations automatically.
  13. Monitor Rolling Remediation: vLCM remediates one host at a time within the cluster. The sequence is: DRS evacuates VMs from the host → host enters Maintenance Mode → vLCM applies the image (installs/removes VIBs, firmware updates) → host reboots → vLCM validates post-remediation compliance → host exits Maintenance Mode → DRS rebalances VMs. Monitor progress in the Tasks and Events pane. Typical per-host duration is 20–45 minutes including reboot.
  14. Handle Remediation Failures: If a host fails remediation, vLCM will pause and flag the error. SSH into the affected host and check /var/log/esxupdate.log for the specific failure reason. Common causes: VIB signature validation failure, hardware incompatibility, network timeout to the depot. Resolve the issue, then retry remediation for the failed host individually to avoid blocking the rest of the cluster rollout.
  15. Post-Remediation Compliance Check: Once all hosts are remediated, run a final compliance check from the Updates tab. All hosts should show Compliant. If any hosts remain Non-compliant, investigate individually. Check the ESXi version on each host via the host Summary tab or SSH: vmware -v and esxcli system version get.
  16. Validate Cluster Health: After remediation, check vSphere HA status, DRS load balance, and all VMkernel connectivity. Verify VMs are distributed correctly across hosts. Run a test vMotion. Check vCenter alarms for any post-patch warnings (NIC driver version changes, storage adapter reconfiguration). Review the vCenter events log for any anomalies during the remediation window.
  17. Update vCenter Server: After patching ESXi hosts, update vCenter Server itself using VAMI (https://<vCSA-IP>:5480) → Update → Check Updates. Apply the latest vCenter patch. vCenter must always be at the same or higher version than the ESXi hosts it manages. Take a vCSA snapshot via the File-based backup or snapshot before applying the vCenter update.
  18. Document & Close Change: Record the pre- and post-patch ESXi versions, remediation date, hosts patched, any failures and resolutions, and the vLCM image name/version used. Update the CMDB with the new ESXi patch level. Close the change management ticket with full remediation notes. Retain the vLCM image definition as the new baseline for future compliance comparisons.

ESXi Patching Procedure

VMware · Maintenance
  1. Review Patch Bulletin & Release Notes: Download the target ESXi patch from the VMware patch portal. Review the release notes for known issues, resolved CVEs, deprecated features, and required minimum vCenter version. Confirm the patch is compatible with your hardware (check VMware HCL) and with any third-party VIBs (NetApp VAAI, Cisco VIC drivers, etc.) currently installed on the hosts.
  2. Plan the Patching Scope: Determine which hosts require patching. Check current ESXi version on all hosts: esxcli system version get. Identify hosts already on the target version (skip) vs. hosts requiring the patch. Plan the patching order — patch non-production or development hosts first to validate the patch before applying to production. Ensure the cluster can tolerate N-1 host capacity during each host's maintenance window.
  3. Pre-Patching Health Check: In vSphere Client, verify the cluster status shows no existing warnings or errors. Check vSphere HA admission control — confirm the cluster has sufficient failover capacity (at least one host's worth of resources free). Verify all datastores are accessible to all hosts and there are no storage multipath degradations. Resolve any outstanding issues before starting.
  4. Take VM Snapshots / Confirm Backups: Take snapshots of all critical VMs (management VMs, AD controllers, databases) via vSphere Client → right-click VM → Snapshots → Take Snapshot. Confirm most recent backup jobs completed successfully. Verify snapshot delta usage is being monitored — remove snapshots after patching is validated to prevent disk bloat.
  5. Check HCL Compatibility: For each patch, verify all physical adapters (NIC, HBA, storage controller) on the host remain on the VMware HCL with the new ESXi version. Check whether any third-party VIBs installed on the hosts are compatible with the target patch level. Use the VMware Compatibility Guide and the patch's component advisory notes.
  6. Download Patch Bundle: Download the offline patch bundle (.zip) from the VMware patch portal. Upload the bundle to a datastore accessible by the host being patched, or to vCenter Update Manager / vLCM depot. Verify the SHA256 checksum of the downloaded file against the value published on the VMware portal before uploading.
  7. Enable SSH on Host: Enable SSH on the target host via vSphere Client → Host → Configure → Services → SSH → Start. Alternatively, enable from DCUI (F2 → Troubleshooting Options → Enable SSH). Note the enabling in the change log — SSH should be disabled again after patching per security policy.
  8. Put Host in Maintenance Mode: Right-click the host in vSphere Client → Maintenance Mode → Enter Maintenance Mode. With DRS fully automated, VMs will live-migrate to other hosts automatically. With DRS manual or disabled, migrate VMs manually using vMotion before entering Maintenance Mode. Wait for all VMs to evacuate — the host cannot be patched if powered-on VMs remain unless you use the Move powered-off and suspended VMs option.
  9. Apply Patch via esxcli (Offline Bundle): SSH into the host and run: esxcli software profile update -d /vmfs/volumes/<datastore>/<patch.zip> -p ESXi-<version>-standard. Use update (not install) to preserve existing VIBs not in the bundle. For applying individual VIBs: esxcli software vib update -d /vmfs/volumes/<datastore>/<vib.zip>. Note: if applying via vLCM or Update Manager, use the UI method instead (see vLCM SOP).
  10. Verify Pre-Reboot Patch Status: After the esxcli command completes, review the output — confirm the VIBs list shows the new patch components as Installed or Updated. Check for any skipped or failed VIBs in the output. If any required VIBs failed to install, investigate the error before rebooting — a reboot in a partially patched state can leave the host inconsistent.
  11. Reboot the Host: Reboot the host: reboot from SSH, or right-click host in vSphere Client → Reboot. The host will disconnect from vCenter during the reboot. Wait for the host to reconnect — typically 5–10 minutes depending on hardware POST and ESXi boot time. Monitor the host reconnection status in vCenter's Recent Tasks pane.
  12. Verify ESXi Version Post-Reboot: Once the host reconnects to vCenter, SSH back in and run vmware -v and esxcli system version get to confirm the new ESXi version and patch level. Check the host Summary tab in vSphere Client for the updated version string. Confirm no critical alarms are firing on the host post-reboot.
  13. Validate Services & Storage: Verify all ESXi services are running: esxcli system process list | grep -i sfcb and /etc/init.d/hostd status. Re-scan storage adapters and confirm all datastores are accessible and showing the correct number of paths: esxcli storage core path list | grep -i active. Check that all VMkernel adapters are online and pingable from the host.
  14. Exit Maintenance Mode: Right-click the host in vSphere Client → Maintenance Mode → Exit Maintenance Mode. DRS (if Fully Automated) will begin rebalancing VMs back onto the patched host. Monitor the DRS migration activity and host resource utilisation during the rebalancing period. Confirm VMs land correctly and no HA or DRS alarms are triggered.
  15. Test Host Functionality: Perform a test vMotion from the patched host to another host and back. Verify vMotion completes without errors, confirming network, storage, and compute are functioning correctly post-patch. Check for any vmkernel connectivity warnings in the host's Configuration → Networking view.
  16. Remove Snapshots: Once the host is validated and VMs are running correctly post-patch, remove the pre-patch VM snapshots: right-click VM → Snapshots → Delete All Snapshots. Monitor datastore space during consolidation — large snapshot chains take time to consolidate and temporarily increase storage usage. Confirm all snapshot trees are clean after deletion.
  17. Disable SSH: After patching is complete and validated, disable SSH on the host: vSphere Client → Host → Configure → Services → SSH → Stop. Set the SSH service startup policy to Start and stop manually (not automatic). This reduces the attack surface and complies with CIS VMware Benchmark recommendations.
  18. Repeat for All Hosts: Repeat Steps 7–17 for each remaining host in the cluster, patching one host at a time to maintain cluster availability. After all hosts are patched, run a final vSphere HA and DRS status check to confirm the cluster is fully healthy and all hosts are at the new patch level.
  19. Document & Close Change: Update the CMDB with the new ESXi version for each host. Record the patch bulletin ID, patching date, engineer name, and any issues encountered. Close the change management ticket. Retain the pre-patch backup and snapshot information per the organisation's retention policy. Notify stakeholders of successful completion.

P2V & V2V Migration

VMware · Migration
  1. Discovery & Assessment: Inventory the source servers — collect OS version, disk count and size, NIC configuration, installed applications, services, and dependencies. Use VMware vCenter Converter Standalone's built-in assessment or a discovery tool (Movere, RVTools, or manual audit). Confirm no physical server features are in use that cannot be virtualised (hardware dongles, physical TPM without vTPM, etc.).
  2. Dependency Mapping: Document all application dependencies — which services communicate with the source server, on which ports, and from which source IPs. Check for hardcoded IP addresses in applications or configurations. Identify any application-level clustering (MSCS, Oracle RAC) that requires special handling during migration. Map backup jobs, monitoring agents, and management tools that must be reconfigured post-migration.
  3. Capacity Planning: Confirm the target vSphere cluster has sufficient CPU, memory, storage, and network capacity to accommodate the migrated VM. Calculate the VM sizing — match physical server resources or right-size based on actual performance data (avoid over-provisioning vCPUs, which can cause CPU scheduler contention). Reserve appropriate datastore space (at least 110% of used disk space to accommodate conversion overhead).
  4. Download & Install VMware Converter: Download VMware vCenter Converter Standalone from the VMware portal. Install it on a conversion server that has network access to both the source physical/virtual machine and the target vCenter/ESXi host. For agent-based conversion, the Converter agent will also be installed on the source machine. For agentless conversion, only the conversion server requires Converter.
  5. Pre-Migration Snapshot (V2V) / Backup (P2V): For V2V migrations: take a VM snapshot of the source VM to create a point-in-time recovery option. For P2V migrations: perform a full server backup (Veeam, Commvault, or Windows Server Backup) before starting the conversion. This ensures a rollback path if the migration fails or post-migration issues are discovered.
  6. Notify Stakeholders & Schedule Downtime: Communicate the migration window to application owners and business stakeholders. For hot (live) P2V/V2V migrations, the source server remains running during conversion (with a brief cutover outage at the end). For cold migrations, the source must be powered off — schedule a maintenance window with appropriate advance notice. Update the change management ticket with the planned cutover time.
  7. Configure Conversion Job — Source: In VMware Converter, click Convert Machine. Select source type: Powered on machine (P2V live or V2V running), VMware Infrastructure virtual machine (V2V from one vCenter to another), or Backup image or third-party virtual machine. Enter source machine IP and credentials. For agent-based: Converter will deploy and start the agent on the source automatically.
  8. Configure Conversion Job — Destination: Select destination type as VMware Infrastructure virtual machine. Enter the target vCenter FQDN and credentials. Choose the target datacenter, cluster/host, and datastore. Select the VM network port group for each NIC. Choose the disk format — Thin Provision (saves space, grows on demand) or Thick Lazy-Zeroed (better performance for production).
  9. Configure Data to Copy: In the Converter job wizard, review the volumes to convert. Exclude any volumes not required in the VM (e.g., raw data drives that will be replaced by SAN/NFS storage in the target environment). Set the destination disk size for each volume — you can resize disks during conversion (increase only; shrinking requires OS-level tools post-migration). Choose to copy only used disk sectors to speed up conversion.
  10. Handle VSS Snapshots (Windows P2V): For live Windows P2V conversions, VMware Converter uses Microsoft VSS (Volume Shadow Copy Service) to create a consistent snapshot of the source for conversion. Ensure the VSS service is running on the source and that sufficient free space (at least 10% of each volume) is available for shadow copy creation. If VSS fails, the conversion will fall back to a crash-consistent copy — acceptable for most workloads but not for databases.
  11. Run Conversion & Monitor Progress: Start the conversion job. Monitor progress in the Converter UI — the job displays current status, data transfer rate, estimated time remaining, and any warnings. A live P2V job runs the initial copy while the source is still running (this can take hours for large disks), then performs a final synchronisation delta copy during the cutover window.
  12. Perform Final Sync & Cutover: For live conversions: once the initial copy completes, schedule the final sync (which requires a brief source shutdown or quiescing). Power off the source server (or coordinate with the application team for the cutover window), run the final synchronisation in Converter to capture any changed blocks since the initial copy, then power on the new VM. Cutover windows are typically 15–30 minutes.
  13. Post-Migration — Install VMware Tools: Power on the migrated VM and log in via console. Install VMware Tools immediately: In vSphere Client → right-click VM → Guest OS → Install VMware Tools. Follow the installation wizard. VMware Tools is required for proper VM management, heartbeat monitoring, graceful shutdown, time synchronisation, and network driver optimisation (replaces emulated E1000 with VMXNET3).
  14. Post-Migration — Upgrade Virtual Hardware: After installing VMware Tools, upgrade the virtual hardware version to match the target ESXi host level: right-click VM → Compatibility → Upgrade VM Compatibility. Higher hardware versions unlock additional features (more vCPUs, larger memory, NVMe virtual disk controllers, vGPU support). Requires a VM power cycle to take effect. Verify the OS boots correctly after the hardware upgrade.
  15. Post-Migration — Reconfigure Network: If the migrated VM has a different IP on the target network (different VLAN or subnet), update the IP address, subnet mask, gateway, and DNS within the guest OS. Update DNS A and PTR records to reflect the new IP. Check that all dependent services (monitoring agents, backup clients, application connections) are updated with the new IP or hostname as required.
  16. Post-Migration — Reconfigure Applications & Services: Review application configurations for any hardcoded physical server references (MAC addresses, physical disk paths, hardware-specific settings). Reconfigure backup agents to target the new VM. Update monitoring (SCOM, Nagios, Zabbix) to monitor the VM via vCenter rather than the physical server. Re-register any application licences that are tied to hardware identifiers if they changed during migration.
  17. Validation Testing: Perform application-level validation: test all critical application functions, verify database connectivity, run smoke tests, check web service responses, and validate data integrity. Involve the application owner in sign-off testing. Review Windows Event Logs or Linux syslog for any driver errors or service startup failures that occurred after the migration.
  18. Performance Baseline Comparison: Monitor the migrated VM's CPU, memory, disk I/O, and network performance for 24–72 hours post-migration. Compare against pre-migration baselines. Common post-P2V issues include: high CPU ready time (too many vCPUs over-scheduled), slow disk I/O (thick provision on a thin pool), or NIC throughput degradation (using E1000 instead of VMXNET3). Adjust VM configuration as needed.
  19. Decommission Source Server: Once the migrated VM is validated, stable, and signed off by the application owner, plan the decommission of the source physical or virtual server. Retain the source for a stabilisation period (typically 2–4 weeks) before full decommission. Remove from DNS, Active Directory, backup schedules, monitoring, and patch management. Wipe disks and return hardware to the asset pool or raise a disposal request per organisational policy.
  20. Document & Update CMDB: Update the CMDB to reflect the new VM (vCenter location, datastore, cluster, IP, OS version, application) and mark the source physical/virtual server as decommissioned. Record migration date, engineer, conversion method (hot/cold, agent/agentless), any issues encountered, and post-migration changes made. Close the migration change ticket.

VMware NSX Micro-Segmentation

VMware · Security
  1. Prerequisites & Planning: Confirm NSX-T Data Center (or NSX-V for legacy environments) licences are available. Verify vSphere hosts are running compatible ESXi versions. Plan the transport zone design (overlay for east-west, VLAN for north-south), edge node sizing, and the micro-segmentation policy model (zone-based isolation vs. application-level DFW rules). Document the application tiers and required traffic flows before writing any rules.
  2. Deploy NSX Manager: Download the NSX Manager OVA from the VMware portal. Deploy it via vSphere Client → Actions → Deploy OVF Template onto a dedicated management cluster or host. Assign a static IP, FQDN, gateway, and DNS. Set the admin and root passwords. During deployment, select the appropriate form factor (Small for lab, Medium for production). NSX Manager serves as the centralised management, control, and data plane configuration node.
  3. Register NSX with vCenter: In the NSX Manager UI (https://<NSX-Manager-IP>), navigate to System → Fabric → Compute Managers → Add. Enter the vCenter FQDN, admin credentials, and accept the certificate thumbprint. This integration allows NSX to discover vSphere inventory (VMs, hosts, clusters, port groups) and push NSX kernel modules to ESXi hosts.
  4. Configure Transport Zones: In NSX Manager → System → Fabric → Transport Zones, create: an Overlay Transport Zone for east-west VM-to-VM traffic using GENEVE encapsulation (e.g., TZ-Overlay), and a VLAN Transport Zone for physical network uplinks on edge nodes (e.g., TZ-VLAN). Transport zones define the scope across which logical segments can span.
  5. Create Host Transport Node Profile: Navigate to System → Fabric → Profiles → Host Transport Node Profiles → Add. Select the overlay transport zone, assign uplink profiles (defining NIC teaming, MTU 1600+ for GENEVE), and map physical NICs (vmnics) to uplinks. This profile is applied to all ESXi hosts in the cluster uniformly. NSX will configure each host with NSX kernel modules (netcpa, nsx-proxy) automatically when the profile is applied.
  6. Prepare ESXi Hosts (Host Transport Nodes): In NSX Manager → System → Fabric → Nodes → Host Transport Nodes, select the vSphere cluster and apply the Host Transport Node Profile. NSX will install the NSX kernel modules on each host and configure them as transport nodes. Monitor the configuration status — each host will show Success when NSX is installed and the datapath is configured. Hosts may briefly disconnect from vCenter during module installation.
  7. Deploy NSX Edge Nodes: Edge nodes provide north-south routing and gateway services. In NSX Manager → System → Fabric → Nodes → Edge Transport Nodes → Add Edge VM. Choose the deployment form factor (Medium: 4 vCPU/8 GB for most production workloads; Large for high-throughput gateways). Deploy the Edge VM onto the management or compute cluster, connect its uplinks to the VLAN transport zone for physical network connectivity, and the overlay zone for east-west communication.
  8. Create an NSX Edge Cluster: Group two or more Edge nodes into an Edge Cluster for HA: NSX Manager → System → Fabric → Nodes → Edge Clusters → Add. Select the two Edge VMs. The Edge Cluster is required before creating Tier-0 and Tier-1 Gateways. For production environments, deploy Edge nodes on separate physical hosts and use anti-affinity rules to ensure they don't run on the same ESXi host simultaneously.
  9. Create Tier-0 Gateway: In NSX Manager → Networking → Tier-0 Gateways → Add. Select the Edge Cluster and configure the HA mode (Active-Active for equal-cost multipath or Active-Standby for simpler setups). Add uplink interfaces on the Edge nodes — assign IPs on the physical network VLANs. Configure BGP or static routing peering with the physical upstream routers to advertise NSX overlay network prefixes to the physical network.
  10. Create Tier-1 Gateway: In NSX Manager → Networking → Tier-1 Gateways → Add. Link the Tier-1 to the Tier-0 Gateway. Tier-1 gateways provide routing services to overlay segments and are typically dedicated per application or per environment (e.g., T1-Production, T1-DMZ). Enable route advertisement to allow Tier-1 connected subnets to be advertised up to Tier-0 and onwards to the physical network.
  11. Create Overlay Segments (Logical Switches): In NSX Manager → Networking → Segments → Add Segment. For each application tier, create a dedicated segment: e.g., Seg-Web-192.168.10.0/24, Seg-App-192.168.20.0/24, Seg-DB-192.168.30.0/24. Connect each segment to the Tier-1 Gateway and set the gateway IP (the default gateway for VMs on that segment). Connect VMs to these segments by changing their port group to the NSX segment.
  12. Create NSX Tags & Groups (Security Groups): In NSX Manager → Inventory → Tags, define tags for classification (e.g., AppTier=Web, AppTier=App, AppTier=DB, Environment=Production). Apply tags to VMs via the NSX Manager VM inventory. Then create Security Groups in Policy → Groups → Add Group using membership criteria: Tag equals AppTier=Web. Groups are dynamic — newly deployed VMs with matching tags automatically join the group.
  13. Design the DFW Rule Policy: Plan the Distributed Firewall (DFW) policy using a whitelist (deny-by-default) approach. Structure the policy into: Emergency rules (top — allow management access, block known-bad sources), Application rules (allow specific inter-tier flows), Infrastructure rules (allow DNS, NTP, domain controllers, backup agents), and a Default deny rule at the bottom. Start with monitoring mode before enforcing.
  14. Create DFW Security Policies: In NSX Manager → Security → Distributed Firewall → Add Policy. Create a policy per application (e.g., CRM-Application-Policy). Add rules within the policy: set Source group, Destination group, Service (TCP/UDP + port), and Action (Allow/Drop/Reject). Example rule: Source=Group:Web, Destination=Group:App, Service=TCP:8080, Action=Allow. Keep rules specific — avoid broad Any/Any rules except for the initial migration period.
  15. Enable DFW in Monitor Mode: Set the policy mode to Monitor before enforcing. In Monitor mode, the DFW logs which traffic matches and which traffic would be blocked (without actually dropping packets). Review the DFW flow logs under Monitor → Logs → Firewall to identify any unaccounted traffic flows and add missing allow rules. Run Monitor mode for at least 48–72 hours for production workloads before switching to enforcement.
  16. Create Service/Application-Level Rules (Layer 7): NSX DFW supports Layer 7 App-ID filtering (context-aware firewall). Create rules using App-ID services (e.g., allow HTTPS rather than just TCP 443) to filter specific application protocols. Use Context Profiles in rules to restrict specific Active Directory operations, database protocols, or web application traffic with finer granularity than port-level filtering alone.
  17. Enforce DFW Rules: After validating Monitor mode logs confirm all legitimate traffic is accounted for, change the policy action to Apply (Enforce). Communicate the enforcement date to application owners. Monitor application functionality immediately after enforcement. The DFW is enforced at the vNIC level of each VM, so rules are applied regardless of which host the VM is running on — fully consistent across the cluster.
  18. Configure NSX Intelligence / Flow Analysis: If NSX Intelligence is licenced, enable it for visualised traffic flow analytics. NSX Intelligence provides a topology view of all east-west flows, recommended rule suggestions based on observed traffic, and a compliance dashboard showing which VMs are protected by DFW policies vs. exposed. Use the recommendation engine to auto-generate initial DFW rules from observed traffic patterns.
  19. Integrate with SIEM: Configure NSX to forward DFW flow logs and security events to the SIEM (Splunk, QRadar, Microsoft Sentinel) via syslog. In NSX Manager → System → Fabric → Syslog, add the SIEM collector. DFW events include allowed flows, dropped connections, and IDS/IPS alerts. Correlating NSX logs in the SIEM enables detection of lateral movement, policy violations, and anomalous east-west traffic patterns.
  20. Document & Lifecycle Management: Export the NSX configuration (System → Backup & Restore → Backup) and store in a version-controlled repository. Document all segment IPs, Tier-0/Tier-1 topology, DFW policy hierarchy, group membership criteria, and tag taxonomy. Establish a review cadence (quarterly) to audit DFW rules for stale entries, orphaned groups, or overly permissive rules. Update policies whenever new application tiers are deployed or decommissioned.

VMware Horizon VDI Setup

VMware · VDI
  1. Prerequisites & Sizing: Confirm vSphere infrastructure has sufficient CPU, memory, and storage for VDI workloads. Plan the desktop pool types (Instant Clone for stateless, Full Clone for persistent). Verify Active Directory is healthy and a dedicated OU exists for VDI computer objects. Confirm licences for Horizon (Horizon Standard, Advanced, or Enterprise) are available and cover the planned desktop count.
  2. Deploy vCenter & Configure vSphere: Ensure a vSphere cluster is dedicated or reserved for Horizon desktops. Enable DRS (Fully Automated) and HA. Create a dedicated Resource Pool for VDI workloads to prevent desktop VMs from competing with infrastructure VMs. Create a dedicated datastore cluster for VDI using storage vMotion-aware datastores. For large deployments, consider vSAN with Horizon-optimised deduplication and compression profiles.
  3. Install Horizon Connection Server (Primary): Download Horizon Connection Server from the VMware portal. Install on a dedicated Windows Server 2019/2022 VM (not a domain controller). During installation, select Horizon Standard Server and specify the Horizon LDAP recovery password. The first Connection Server creates the Horizon LDAP (AD LDS) instance. Minimum: 4 vCPU, 10 GB RAM per Connection Server. Run as a domain-joined VM in the Horizon OU.
  4. Install Horizon Connection Server (Replica): For HA, install a second Connection Server on a separate VM. Select Horizon Replica Server during installation and point it to the primary Connection Server IP. The replica replicates the LDAP configuration in real-time. Deploy a minimum of two Connection Servers for production. Place a load balancer (F5, NSX, or Windows NLB) in front of the Connection Servers for client connections.
  5. Configure Horizon Administrator — vCenter Integration: Log in to the Horizon Administrator console (https://<Connection-Server-FQDN>/admin). Navigate to View Configuration → Servers → vCenter Servers → Add. Enter the vCenter FQDN and credentials. Accept the certificate thumbprint. Configure the Instant Clone Domain Account (a dedicated service account in AD with permissions to create and join computer objects in the VDI OU).
  6. Create the Golden Master Image (Parent VM): In vCenter, create a new Windows VM (Win 10/11 Enterprise or Windows Server for RDSH). Install the OS with all Windows updates applied. Remove bloatware and disable unnecessary services and scheduled tasks. Configure power settings to High Performance. Install required applications (Office, browsers, VPN clients, endpoint protection). Do NOT join the parent VM to the domain yet — domain join happens at pool deployment time for Instant Clones.
  7. Optimise the Golden Image: Run the VMware OS Optimisation Tool (OSOT) on the parent VM. OSOT disables unnecessary Windows services (SuperFetch, Windows Search indexing, unnecessary scheduled tasks), configures optimal registry settings, and prepares the image for VDI performance. Choose the appropriate template (Windows 10/11 Non-Persistent). Review each optimisation recommendation before applying — some may impact specific applications.
  8. Install VMware Horizon Agent: On the parent VM, install the Horizon Agent from the Horizon media: VMware-viewagent-x86_64.exe /s /v"/qn VDM_VC_MANAGED_AGENT=1". Select components to install: 3D rendering (if GPU is configured), USB redirection, Clipboard Redirection, HTML Access, Smart Card SSO, Teams Optimisation (if using Microsoft Teams). Do not enable the Horizon Agent service to start automatically — it will be configured at pool deployment.
  9. Take a Parent Snapshot: In vCenter, take a snapshot of the parent VM: right-click → Snapshots → Take Snapshot. Name it descriptively with the date and content version (e.g., Win10-21H2-Office365-v1.0-2024-01). This snapshot is the baseline for the Instant Clone pool. All pool desktops are derived from this snapshot. Do not delete this snapshot while the pool is active — it is required for desktop provisioning.
  10. Create an Instant Clone Desktop Pool: In Horizon Administrator → Catalog → Desktop Pools → Add → Automated Desktop Pool → Instant Clone. Configure: Pool ID, Display Name, user assignment (Floating for non-persistent, Dedicated for persistent). Set the minimum, maximum, and spare desktop counts. Select the parent VM and snapshot. Choose the target cluster, datastore, and the AD OU where desktop computer objects will be created. Set the naming pattern (e.g., VDI-{n:fixed=4}).
  11. Configure Pool Policies & Settings: In the pool configuration, set: session timeout policies (disconnect after 15 min idle, log off after 120 min disconnected), Power Policy (ensure VMs suspend or power off when not in use to save resources), display protocol (Blast Extreme as default, with PCoIP as secondary). Configure Client Restrictions to limit access by client type or IP range if needed.
  12. Configure App Volumes (Application Delivery): If application layering is required, deploy App Volumes Manager as a separate Windows VM. Install the App Volumes Agent on the golden image (before taking the pool snapshot). In App Volumes Manager → Volumes → Create Package. Install applications in a packaging VM to create AppStacks or writable volumes. Attach packages to AD users or groups — applications are delivered on-demand at login without being baked into the base image.
  13. Configure Dynamic Environment Manager (DEM/UEM): Deploy VMware Dynamic Environment Manager for user profile and policy management. Install the DEM Agent on the golden image. Configure a DEM share on a file server. Create DEM Smart Policies for application settings, drive mappings, printer connections, and environment variables. DEM replaces traditional roaming profiles and enables fast logins with personalised, policy-driven user environments for non-persistent desktops.
  14. Configure Unified Access Gateway (External Access): Deploy VMware Unified Access Gateway (UAG) OVA in the DMZ for external user access. UAG proxies Blast/PCoIP connections and handles two-factor authentication (RSA SecurID, RADIUS, SAML). Configure the UAG to point to the internal Connection Server load balancer. Set up SSL certificates on UAG using a publicly trusted CA certificate. Configure firewall rules to allow TCP/UDP 443 and TCP 8443 from the internet to UAG.
  15. Entitle Users to Desktop Pools: In Horizon Administrator → Catalog → Desktop Pools → select pool → Entitlements → Add. Search for AD users or groups and add them as entitled. Only entitled users can see and connect to the pool in Horizon Client. Use AD groups (rather than individual users) for easier administration — add or remove users from the pool by managing AD group membership.
  16. Test End-to-End Connectivity: Install Horizon Client on a test endpoint. Connect to the Connection Server FQDN (internal) or UAG FQDN (external). Log in with an entitled AD user. Launch a desktop session and verify: display resolution, clipboard redirection, USB device pass-through, drive redirection, audio, and Teams media optimisation (if configured). Test from both internal and external network paths.
  17. Configure Monitoring & Alerts: In Horizon Administrator → Monitor, review session counts, problem desktops, and event logs. Configure vRealize Operations for Horizon (or VMware Aria Operations for Horizon) for deep performance analytics — tracks login duration breakdown, Blast display protocol metrics, ESXi host utilisation per VDI cluster, and user experience scoring. Set alerts for session spike thresholds and provisioning failures.
  18. Golden Image Update Process: When updating the golden image (OS patches, application updates): power on the parent VM, apply changes, shut it down, take a new snapshot (e.g., v1.1-2024-04). In Horizon → Desktop Pool → Edit → select the new snapshot. Schedule the push — desktops are re-provisioned from the new snapshot at next logout (non-persistent) or on next scheduled maintenance. Maintain at least two versions of the parent snapshot for rollback capability.
  19. Document & Handover: Document the architecture: Connection Server FQDNs, load balancer VIP, UAG IP, pool configurations, golden image version, App Volumes config, DEM share path, AD OUs, and service account details. Create an operational runbook covering daily health checks, pool scaling procedures, image update process, and troubleshooting steps. Update the CMDB and notify the service desk of the go-live.

vSAN Configuration

VMware · Storage
  1. Prerequisites — Hardware: Confirm minimum 3 ESXi hosts for a standard vSAN cluster (2 hosts + witness appliance for stretched cluster). Each host needs: at least one NVMe or SSD device for the cache tier, one or more SSD/NVMe/HDD devices for the capacity tier (All-Flash recommended for production). Verify all disks and controllers are on the VMware vSAN HCL — non-HCL hardware is unsupported and can cause data corruption.
  2. Prerequisites — Network: Each ESXi host must have a dedicated VMkernel adapter for vSAN traffic. Minimum bandwidth: 1 GbE (lab only), 10 GbE strongly recommended for production, 25/100 GbE for high-performance all-flash workloads. Configure jumbo frames (MTU 9000) on the vSAN VMkernel, the vDS port group, and the physical switch ports/trunk. Verify end-to-end MTU with vmkping -I vmk2 -d -s 8972 <vSAN-IP-of-another-host>.
  3. Create the vSphere Cluster: In vSphere Client, create a cluster under the datacenter. Ensure vSphere HA and DRS are planned for enablement. Add all ESXi hosts to the cluster. Confirm all hosts are accessible, have no critical errors, and all disk devices intended for vSAN are not currently used by any datastore. vSAN will claim unclaimed disks — do not pre-format or partition them.
  4. Configure vSAN VMkernel Adapter: On each ESXi host, create a VMkernel adapter dedicated to vSAN: Host → Configure → Networking → VMkernel Adapters → Add. Select the vSAN port group (a dedicated VLAN is recommended). Assign a static IP in the vSAN network subnet. Enable the vSAN traffic type on the VMkernel. Verify the adapter is pingable from all other hosts in the vSAN subnet.
  5. Enable vSAN on the Cluster: Select the cluster → Configure → vSAN → Services → Configure. Choose the deployment type: Single Site Cluster (standard), Stretched Cluster (two sites + witness), or 2-Node Direct Connect (robo/edge). Select the disk claiming type: Automatic (vSAN claims all eligible unclaimed disks — recommended) or Manual (you choose specific disks per host). Choose All-Flash or Hybrid mode based on your hardware.
  6. Claim Disks & Create Disk Groups: In automatic mode, vSAN forms disk groups automatically — one cache-tier device (NVMe/SSD) paired with one or more capacity-tier devices per disk group. In manual mode, go to vSAN → Disk Management, select each host, and click Claim Disks. Assign each device to either the Cache tier or Capacity tier. A disk group must have exactly one cache device. Best practice: limit disk groups to 7 capacity devices per cache device for performance balance.
  7. Configure vSAN Fault Domains (Rack Awareness): For clusters with hosts across multiple physical racks, configure Fault Domains to ensure vSAN component placement respects rack-level failure boundaries. In vSAN → Fault Domains → Add Fault Domain. Group hosts in the same physical rack into a fault domain. vSAN will then ensure VM components (data, witness, mirror) are distributed across fault domains so a full rack failure doesn't cause data loss.
  8. Configure Deduplication & Compression (All-Flash only): After the cluster is formed, enable space efficiency features for All-Flash clusters: Cluster → Configure → vSAN → Services → Edit → enable Deduplication and Compression. This processes data on the capacity tier to reduce consumed space. Note: enabling deduplication requires a full rolling disk reformat — plan for increased I/O during the process. For Hybrid (SSD + HDD) clusters, only Compression is available.
  9. Enable Encryption (if required): For regulated workloads (HIPAA, PCI-DSS), enable vSAN Data-at-Rest Encryption: Cluster → Configure → vSAN → Services → Edit → enable Encryption. Requires a KMS (Key Management Server) to be integrated with vCenter (vCenter → Security → Key Providers). Configure the KMS connection first, then enable encryption — vSAN will perform a rolling reformat of all data with encryption applied.
  10. Create VM Storage Policies: In vSphere Client → Policies and Profiles → VM Storage Policies → Create. Define policies using vSAN rules: set Failures to Tolerate (FTT) — FTT=1 allows one host failure (RAID-1: mirroring or RAID-5: erasure coding for 4+ hosts); FTT=2 allows two failures (RAID-6 for 6+ hosts). Set Stripe Width for sequential I/O-intensive workloads. Assign the policy to VMs — vSAN enforces the policy placement automatically.
  11. Configure vSAN iSCSI Target Service (if required): To provide block storage to non-vSphere workloads (physical servers, other hypervisors) from the vSAN datastore, enable the vSAN iSCSI Target Service: Cluster → Configure → vSAN → iSCSI Target Service → Enable. Create iSCSI targets and LUNs, configure CHAP authentication, and add initiator access controls. Assign a VM Storage Policy to each LUN to define redundancy level.
  12. Run vSAN Health Check: Navigate to Cluster → Monitor → vSAN → Health. Run the health check service — it validates: cluster configuration, network (vSAN VMkernel connectivity, MTU, multicast if used), disk (SSD health, capacity balance, disk format version), data (object health, component placement), and performance service status. All checks should show green. Investigate and resolve any WARN or ERROR items before deploying production workloads.
  13. Enable vSAN Performance Service: In Cluster → Configure → vSAN → Services → Performance Service → Enable. This creates a stats database object on the vSAN datastore to store performance metrics. Once enabled, Monitor → vSAN → Performance provides IOPS, throughput, and latency graphs per VM, host, disk group, and disk. This is essential for capacity planning and troubleshooting performance issues.
  14. Configure vSAN Skyline Health (optional): If the environment is connected to VMware Skyline, enable health data collection to forward vSAN health telemetry to VMware for proactive support and early issue identification. Configure in vCenter → Administration → Skyline → Skyline Health. This is optional but recommended for environments with active VMware Production Support contracts.
  15. Enable vSphere HA on the vSAN Cluster: With vSAN configured, enable vSphere HA on the cluster. vSAN and HA integrate tightly — HA uses the vSAN datastore for VM heartbeat and stores metadata about which hosts have accessed which objects. Under HA → Advanced Options, ensure das.ignoreRedundantNetWarning=true is set if vSAN and management VMkernels share the same physical path (this prevents a false redundancy warning).
  16. Deploy Test VMs & Validate Storage Policies: Create a test VM on the vSAN datastore. Assign a VM Storage Policy (FTT=1). Verify the policy compliance shows Compliant in the VM's summary. Check VM Object Health in vSAN → Virtual Objects — each VM should show all components as Active. Run a VM I/O stress test (IOmeter, fio) and confirm latency and IOPS match expected performance for the hardware tier.
  17. Test Failure Scenarios: Simulate a disk failure: remove a capacity disk from a disk group (in a lab environment or during a controlled test) and verify vSAN begins rebuilding the affected objects, rebalancing data across remaining disks. Confirm no VMs go offline. Test host failure (put a host in Maintenance Mode with Full Data Migration) and verify all VM objects rebuild to compliance. Review Skyline Health and vSAN events during the test.
  18. Configure Proactive Rebalancing: For clusters where disk usage is unbalanced across hosts or disk groups, enable proactive rebalancing: Cluster → Configure → vSAN → Disk Management → Rebalance. vSAN will redistribute data to equalise consumption. Configure the rebalance threshold (default: trigger rebalance when a disk deviates more than 30% from cluster average). Rebalancing runs as a background task and does not impact VM availability.
  19. Document & Update CMDB: Record the vSAN configuration: cluster name, ESXi hosts, disk groups per host (cache and capacity devices, model, capacity), vSAN mode (All-Flash/Hybrid), enabled features (dedup/compression, encryption), fault domains, VM Storage Policies, FTT levels, and total raw vs. usable capacity. Store the vSAN HCL validation report. Update the CMDB and notify the storage team that the vSAN datastore is production-ready.

Snapshot Management

VMware · Infrastructure
  1. Understand Snapshot Mechanics: A vSphere snapshot captures the VM's disk state, memory state (optional), and settings at a point in time. After a snapshot is taken, all writes go to a delta VMDK (child disk) rather than the base disk. Snapshots are not backups — they are change-tracking mechanisms. Long-running or deeply chained snapshots cause performance degradation and datastore bloat. Policy: no snapshot should remain active for more than 72 hours in production.
  2. Pre-Snapshot Checks — Datastore Space: Verify sufficient free space on the datastore before taking a snapshot. The delta disk can grow up to the full size of the base VMDK if the VM has significant write activity. Rule of thumb: ensure at least 20–30% free space on the datastore (or the full size of the VM's disk if the snapshot will be held for more than a few hours). Check free space: Storage → Datastores → Summary tab.
  3. Pre-Snapshot Checks — Existing Snapshot Chain: Check whether the VM already has active snapshots: right-click VM → Snapshots → Manage Snapshots. If an existing chain is present and older than 72 hours, consolidate or delete before adding a new snapshot. Deep snapshot chains (3+ levels) dramatically increase I/O overhead and commit time. Run Get-VM | Get-Snapshot | Where-Object {$_.Created -lt (Get-Date).AddHours(-72)} via PowerCLI to report stale snapshots.
  4. Check for Snapshot Consolidation Needed: Before taking a new snapshot, check if any existing snapshots need consolidation: vSphere Client → VM → Summary tab — look for the Consolidation Needed warning. This indicates orphaned delta files that are not reflected in the snapshot tree. Consolidate first: right-click VM → Snapshots → Consolidate. Do not proceed with a new snapshot if consolidation is needed.
  5. Application Quiescing Decision: Decide whether to quiesce the guest filesystem before snapshotting. Quiesced snapshots (enabled via the Quiesce guest filesystem checkbox) flush in-flight I/O and create an application-consistent state using VSS (Windows) or the quiescing scripts (Linux via VMware Tools). Use quiesced snapshots for databases, AD controllers, and transactional workloads. For non-database VMs where a crash-consistent state is acceptable, quiescing can be skipped.
  6. Memory Snapshot Decision: The Snapshot the virtual machine's memory option captures the full RAM state, allowing you to revert the VM to its exact running state (not just disk state). Use memory snapshots when you need a precise rollback including in-flight application state. Caution: memory snapshots can be large (equal to the VM's configured RAM) and increase snapshot creation time. Do not use memory snapshots for routine pre-patch snapshots where disk state is sufficient.
  7. Take the Snapshot: Right-click the VM → Snapshots → Take Snapshot. Enter a descriptive name: Pre-Patch-KB5023697-2024-03-15 or Pre-App-Upgrade-v2.3-2024-03-15. Add a description with the purpose, requestor, and expected deletion date. Select quiesce and/or memory options as determined above. Click OK. Monitor the task in the Recent Tasks pane — large or memory snapshots may take several minutes to complete.
  8. Validate the Snapshot: After creation, verify the snapshot appears correctly: right-click VM → Snapshots → Manage Snapshots. Confirm the snapshot is shown in the tree with the correct name, timestamp, and parent chain. The You Are Here marker should be on the new snapshot (the active write point). Verify the delta VMDK file exists on the datastore via the Datastore Browser. Confirm the VM is running normally post-snapshot.
  9. Monitor Delta Disk Growth: After taking a snapshot, periodically monitor the delta disk growth in the Datastore Browser or via PowerCLI: Get-VM | Get-Snapshot | Select VM, Name, SizeMB, Created. Alert if delta disk size exceeds 50% of the base VMDK — at this point the commit time and I/O overhead are significant. For write-intensive VMs (databases, log servers), check delta growth every 30–60 minutes during extended snapshot holds.
  10. Snapshot-Based Testing: To test a change (patch, configuration update, application version) with snapshot rollback capability: take the pre-change snapshot, apply the change, validate the change in a testing window, then either delete the snapshot (change successful) or revert to it (change failed). Never use snapshots for production DR or as a replacement for proper backup — they are a temporary safety net only.
  11. Revert to Snapshot (Rollback): If the change requires rollback, right-click VM → Snapshots → Manage Snapshots → select the snapshot → Revert To. Warning: reverting discards all changes made since the snapshot was taken (disk writes, memory state if captured). Power off the VM first if reverting a disk-only snapshot (no memory). After revert, power on the VM and verify the application returns to its pre-change state. Update the change ticket to reflect the rollback.
  12. Create Child Snapshots for Staged Testing (if needed): For multi-stage changes (e.g., applying multiple patches in sequence), take a child snapshot after each successful stage: Snapshot 1 (baseline) → apply patch A → Snapshot 2 → apply patch B → Snapshot 3. This allows rollback to any specific intermediate state. Keep chains shallow (3 levels max) — deeper chains cause severe I/O amplification on the host.
  13. Delete Snapshot After Validation: After the change is validated and the rollback window has passed (typically 24–48 hours), delete the snapshot: right-click VM → Snapshots → Manage Snapshots → select snapshot → Delete. The Delete option commits the delta disk changes into the parent disk (or base disk) and removes the delta file. Monitor the commit task in Recent Tasks — commit time varies from minutes to hours depending on delta size and I/O. The VM remains running during commit.
  14. Delete All Snapshots (Full Cleanup): To remove an entire snapshot tree, use Delete All Snapshots (right-click VM → Snapshots → Delete All Snapshots). This commits all delta disks in the chain into the base disk in a single operation. Warning: for deeply chained or large snapshots, this can cause significant datastore I/O and may temporarily slow VM performance during the commit. Schedule large snapshot commits during off-peak hours.
  15. Consolidate Disks (Orphaned Delta Files): If vSphere reports a Virtual machine disks consolidation is needed warning (visible on the VM Summary tab), run consolidation: right-click VM → Snapshots → Consolidate. This removes orphaned delta VMDK files that exist on the datastore but are not tracked in the snapshot tree (typically left by failed snapshot deletion tasks or snapshots deleted outside of vCenter). Consolidation is non-destructive and runs while the VM is powered on.
  16. Automated Snapshot Monitoring: Deploy automated snapshot monitoring via PowerCLI scheduled tasks or vRealize Operations alerts. Configure vCenter alarms to notify when: a VM has snapshots older than 72 hours, a snapshot delta exceeds 50 GB, or a datastore snapshot footprint exceeds a defined threshold. Example PowerCLI alert: Get-VM | Get-Snapshot | Where {$_.Created -lt (Get-Date).AddHours(-72)} | Select VM, Name, Created, SizeMB | Export-Csv stale_snapshots.csv.
  17. Snapshot Policy & Governance: Document and enforce a snapshot retention policy: maximum snapshot age (72 hours for production, 24 hours for databases), maximum delta size (50% of base disk), maximum chain depth (3 levels), and required naming convention. Integrate snapshot creation and deletion into the change management process — snapshots must be tied to an open change ticket and deleted upon change closure.
  18. Post-Cleanup Validation: After deleting or consolidating snapshots, verify: the VM snapshot tree shows No Snapshots in Manage Snapshots, the datastore space is reclaimed (check free space before and after), and VM performance metrics (CPU ready, disk latency) return to pre-snapshot baselines in vCenter Performance charts. Confirm no Consolidation Needed warning remains on the VM summary.

Nutanix

AHV, Prism Central, AOS, storage, and cluster management procedures

Nutanix Cluster Deployment

Nutanix · Infrastructure
  1. Hardware Prerequisites: Verify all nodes meet minimum requirements — compatible CPU (Intel/AMD), minimum RAM per node, NVMe/SSD drives for CVM, and 10 GbE NICs. Confirm IPMI/BMC access is configured on each node with a reachable IP for remote management.
  2. Download Foundation: Log in to the Nutanix Portal → Downloads → Foundation. Download the latest Foundation VM (OVA/OVF) or Foundation ISO. Verify the SHA256 checksum of the downloaded file before proceeding.
  3. Deploy Foundation VM: Import the Foundation OVA into an existing hypervisor (ESXi or AHV). Assign the Foundation VM a static IP on the same L2 network as the bare-metal nodes. Power on and access the Foundation UI at http://<Foundation-VM-IP>:8000.
  4. Discover Nodes: In the Foundation UI, click Discover Nodes. Foundation uses IPv6 link-local or DHCP to auto-detect unconfigured nodes on the network. Verify all expected nodes appear; manually enter IPMI IPs if auto-discovery fails.
  5. Configure Node IPs: For each discovered node, assign: IPMI/BMC IP (for out-of-band management), AHV Hypervisor Host IP (management network), and CVM IP (Controller VM IP). Ensure all IPs are in the same subnet and do not conflict with existing devices.
  6. Set Cluster Network Details: Define the Cluster Virtual IP (used for Prism Element HA access), Data Services IP (iSCSI/Volume Group access), Subnet Mask, Default Gateway, and DNS Servers. Set the cluster name and desired AOS version.
  7. Select AOS & AHV Images: Upload or select the AOS bundle (.tar.gz) and AHV hypervisor image from the Nutanix portal. Foundation supports imaging multiple versions simultaneously. Confirm the AOS-to-AHV compatibility matrix before selection.
  8. Run Pre-checks: Click Run Preflight to validate network reachability, IPMI connectivity, disk availability, and BIOS/firmware compatibility. Resolve all WARN or FAIL items before proceeding — common issues include IPMI unreachable, insufficient disk count, or duplicate IPs.
  9. Start Imaging: Click Begin Installation. Foundation will remotely boot each node via IPMI/virtual media, write AHV and AOS to the disks, and configure the CVM on each node. Monitor per-node progress bars in the Foundation UI. Imaging typically takes 30–60 minutes per node depending on disk speed.
  10. Form the Cluster: After all nodes are imaged and CVMs are running, Foundation automatically forms the cluster. Alternatively, SSH into any CVM and run: cluster -s <CVM_IP1>,<CVM_IP2>,<CVM_IP3> --cluster_name=<name> create. Wait for all services to start — monitor with cluster status.
  11. Initial Prism Element Login: Open a browser and navigate to https://<Cluster-Virtual-IP>:9440. Log in with default credentials (admin / Nutanix/4u). Accept the EULA and change the admin password immediately. Complete the initial setup wizard.
  12. Configure NTP & DNS: Go to Prism Element → Settings → NTP Servers; add at least two reliable NTP sources (e.g., internal NTP or pool.ntp.org). Under Name Servers, add primary and secondary DNS IPs. Verify time sync across all CVMs via ncli cluster get-ntp-servers.
  13. Configure SMTP & Alerts: In Settings → SMTP Server, configure the mail relay for alert notifications. Set up alert policies under Health → Alerts to notify the infrastructure team on critical events (node failure, disk degradation, replication lag).
  14. Create Storage Container: Navigate to Storage → Containers → Create. Define a container name, enable compression, deduplication, and erasure coding (EC-X) as per workload requirements. Set replication factor (RF2 for 3-node, RF3 for 5+ node clusters).
  15. Configure Network (AHV): Go to Network → Create Network in Prism Element. Define VLANs for VM traffic (e.g., VLAN 100 for production, VLAN 200 for management). Map each virtual network to the corresponding physical uplink/bond on the AHV hosts.
  16. Run NCC Health Check: SSH into any CVM and run ncc health_checks run_all. Review the output for any FAIL or WARN items. Common post-deployment checks include: cluster resiliency, CVM service status, disk health, and network connectivity between nodes.
  17. Register to Prism Central: In Prism Element → Settings → Prism Central Registration → Register. Enter the Prism Central IP and admin credentials. Once registered, the cluster appears in Prism Central for centralised management, policy, and monitoring.
  18. Apply Licence: In Prism Central or Prism Element → Settings → Licensing, apply the appropriate Nutanix licence (Starter, Pro, or Ultimate). Licences unlock features such as Calm, Flow, Leap, and advanced analytics. Verify licence status shows Active.
  19. Deploy Test VM & Validate: Create a test VM in Prism Element or Prism Central on the newly created storage container and network. Power it on, verify console access, ping gateway, and confirm VM placement across nodes. Delete the test VM after validation.
  20. Document & Handover: Record all IP assignments (IPMI, Host, CVM, VIP, DSIP), cluster name, AOS/AHV version, storage container configs, and network VLAN mappings in the CMDB or infrastructure runbook. Share credentials securely and notify the operations team that the cluster is production-ready.

Prism Central Deployment

Nutanix · Management
  1. Prerequisites Check: Confirm the target Nutanix cluster is running AOS 5.5 or later and all nodes are healthy (NCC green). Ensure a static IP is reserved for the Prism Central VM on the management network, along with subnet mask, gateway, and DNS details ready before starting.
  2. Choose Deployment Size: Determine PC deployment size based on managed VM count — Small (up to 2,500 VMs): 4 vCPU, 16 GB RAM, 500 GB storage; Large (up to 25,000 VMs): 8 vCPU, 32 GB RAM, 2 TB storage; Scale-Out (3-node PC): for >25,000 VMs or HA requirements. Document the sizing decision in the deployment plan.
  3. Download Prism Central: Log in to the Nutanix Portal → Downloads → Prism Central. Download the PC deploy bundle (.tar) matching your target AOS version. Verify the SHA256 checksum. Alternatively, initiate the deployment directly from Prism Element if internet access is available on the cluster.
  4. Initiate Deployment from Prism Element: Log in to Prism Element (https://<Cluster-VIP>:9440) → Settings (gear icon) → Prism Central Registration → Deploy Prism Central. Select Deploy and choose whether to upload the bundle manually or download directly from the Nutanix portal.
  5. Configure PC VM Network Settings: In the deployment wizard, enter: PC VM IP Address, Subnet Mask, Default Gateway, and DNS Server IPs. For scale-out PC, enter three separate IPs (one per PC VM) plus a Virtual IP that floats across all three nodes for HA access.
  6. Configure PC VM Resources: Select the target storage container for the PC VM disk. Confirm vCPU and RAM allocation matches the sizing chosen in Step 2. Review the summary screen — ensure there is sufficient free capacity on the cluster before clicking Deploy.
  7. Monitor Deployment Progress: The wizard will upload the PC image, create the VM, and boot it automatically. Monitor the progress bar in Prism Element — deployment typically takes 10–20 minutes. Do not interrupt or close the session. Confirm the task completes in the Task pane with status Succeeded.
  8. Access Prism Central UI: Once deployed, open a browser and navigate to https://<PC-IP>:9440. Log in with default credentials (admin / Nutanix/4u). Accept the EULA, change the admin password immediately, and complete the initial setup wizard including timezone and pulse (phone home) settings.
  9. Register the Local PE Cluster: In Prism Element → Settings → Prism Central Registration → Register. Enter the PC IP and admin credentials. Accept the certificate warning. The local PE cluster will appear in Prism Central → Hardware → Clusters within a few minutes after registration completes.
  10. Register Additional PE Clusters: For each remote Nutanix cluster to be managed centrally, repeat the registration process from that cluster's Prism Element UI pointing to the same Prism Central IP. Alternatively, in Prism Central → Settings → Prism Central Registration → Register New Cluster, provide the PE cluster VIP and credentials.
  11. Configure NTP on Prism Central: In Prism Central → Settings → NTP Servers, add at least two NTP sources. Verify time synchronisation between PC and all registered PE clusters — time skew greater than 5 minutes can cause authentication and replication failures.
  12. Configure SMTP & Alert Policies: Under Settings → SMTP Server, enter the mail relay details. Set up Alert Policies under Activity → Alerts to forward critical alerts (cluster degradation, VM failures, licence expiry) to the infrastructure team distribution list.
  13. Configure Authentication (AD Integration): In Prism Central → Settings → Authentication → Directory Services → Add Directory. Enter the AD/LDAP server URL, service account credentials, search base DN, and test the connection. Map AD groups to Prism Central roles (Cluster Admin, Viewer, User Admin) under Role Mappings.
  14. Apply Nutanix Licence: Go to Settings → Licensing. Apply the appropriate licence key (Pro, Ultimate, or product-specific add-ons like Calm or Flow). Verify the licence status shows Active and the feature entitlements are reflected in the dashboard. Unlicensed features will appear greyed out.
  15. Enable Required Features: Navigate to Settings → Prism Central Settings → Enable Features. Activate any licensed modules required by the organisation — Calm (application automation), Flow (micro-segmentation), Karbon (Kubernetes), Leap (DR orchestration), or Files/Objects. Each enablement triggers a background task — monitor in the Tasks pane.
  16. Configure Categories: In Prism Central → Administration → Categories, create key-value category pairs for VM classification (e.g., Environment: Production/Dev/Test, AppTier: Web/App/DB, Owner: TeamA/TeamB). Categories are used by policies (security, protection, placement) across all registered clusters.
  17. Create VM Management Policies: Set up Image Configuration (centrally managed images available to all clusters), VM Templates, and Network Function Chains if applicable. Define VM placement policies under Policies → VM–Host Affinity or Prism Central-managed DRS-equivalent rules.
  18. Configure Prism Central HA (Scale-Out only): For 3-node PC deployments, verify all three PC VMs are running and the Virtual IP is active. Under Settings → Prism Central Management → Scale Out, confirm the cluster health shows all nodes joined. Test HA by simulating a single PC VM shutdown — the VIP should remain accessible via the remaining nodes.
  19. Run NCC from Prism Central: SSH into the PC VM (ssh nutanix@<PC-IP>) and run ncc health_checks run_all. Review results for any WARN or FAIL items specific to Prism Central services. Common checks include PC-to-PE connectivity, IAM service health, and Atlas/Ergon service status.
  20. Validate & Document: Confirm all registered clusters appear healthy in the Prism Central dashboard. Verify user access with an AD account login test. Document the PC deployment details — PC IP/VIP, version, registered clusters, AD config, feature enablements, and licence keys — in the CMDB or infrastructure runbook. Notify stakeholders that Prism Central is production-ready.

AOS Upgrade Procedure

Nutanix · Patching
  1. Review Upgrade Path & Release Notes: Check the Nutanix compatibility matrix on the portal to confirm the target AOS version is a supported upgrade path from the current version. Read the release notes for known issues, deprecations, and required minimum AHV version. Ensure Prism Central (if deployed) is on a compatible PC version before upgrading AOS.
  2. Pre-Upgrade NCC Health Check: SSH into any CVM and run ncc health_checks run_all 2>&1 | tee /home/nutanix/ncc_pre_upgrade.log. Review the output — all checks must be PASS or INFO. Resolve any WARN or FAIL items (degraded storage, CVM service down, missing heartbeat) before proceeding. Save the log for post-upgrade comparison.
  3. Verify Cluster Resiliency: Run ncli cluster get-domain-fault-tolerance-status type=node to confirm the cluster can tolerate at least one node failure (RF2) or two node failures (RF3). Do not upgrade if the cluster is already in a degraded or rebuilding state — wait for full resiliency before proceeding.
  4. Check Storage Capacity: Confirm free datastore capacity is at least 20% of total cluster storage. AOS upgrade requires temporary working space on each node. Run ncli sp ls to check storage pool usage. Also verify each node's CVM boot disk has sufficient free space (df -h on each CVM — /home/nutanix should have >10 GB free).
  5. Snapshot / Backup Critical VMs: Take application-consistent snapshots of critical workloads (Domain Controllers, databases, management VMs) prior to the upgrade. Confirm existing backup jobs are up to date. Notify application owners of the planned maintenance window — AOS upgrades are non-disruptive but risk mitigation is essential.
  6. Check Pending Alerts & Tasks: In Prism Element → Activity → Tasks, confirm there are no long-running tasks or stuck operations (disk rebuild, snapshot replication, clone tasks). Under Alerts, clear or acknowledge all outstanding critical alerts. Do not start an upgrade while any background tasks are in progress.
  7. Download or Upload AOS Bundle: In Prism Element → Settings → Upgrade Software → AOS, click Download to pull the upgrade bundle directly from the Nutanix portal (requires internet access). If the cluster has no internet access, download the AOS .tar.gz bundle from the Nutanix portal on a jump host and click Upload the AOS binary to upload manually.
  8. Verify Bundle Integrity: After upload, Prism Element automatically validates the checksum. Wait for the status to show Available for Upgrade. If the checksum validation fails, re-download and re-upload the bundle — do not proceed with a corrupted image.
  9. Run Pre-Upgrade Checks (Automated): Click Upgrade next to the validated AOS version. Prism Element will automatically run a second round of pre-upgrade checks — cluster services state, CVM connectivity, host hardware compatibility, and minimum version requirements. Review each check result. If any check fails, the upgrade will not proceed; resolve the issue and re-run.
  10. Initiate the Upgrade: Click Upgrade Now (or Schedule for an off-hours window). Confirm the action in the popup dialog. The upgrade process begins — Nutanix upgrades one CVM at a time in a rolling fashion, keeping the cluster online and VMs running throughout. The first step is a genesis restart on each CVM to activate the new binaries.
  11. Monitor Upgrade Progress: Track the rolling upgrade in Prism Element → Settings → Upgrade Software → AOS. Each node cycles through: Pre-upgrade → Downloading → Upgrading → Rebooting → Done. Monitor the Tasks pane for the overall upgrade task. Typical duration is 15–30 minutes per node. Do not manually reboot or shut down any CVM during this process.
  12. Monitor CVM Services During Rolling Upgrade: While each CVM is upgrading, SSH into a CVM that is not currently upgrading and run cluster status to confirm all services (Cassandra, Stargate, Zookeeper, Prism, etc.) remain running on the active nodes. All VMs should continue running on AHV hosts whose CVMs are healthy.
  13. AHV Upgrade (if required): If the target AOS version requires a newer AHV version, Prism Element will prompt for an AHV upgrade after AOS completes. Proceed through the same rolling process — AHV upgrades put each host into maintenance mode, live-migrate VMs to other hosts, update the hypervisor, reboot, and exit maintenance mode one host at a time.
  14. Post-Upgrade NCC Health Check: Once all nodes show Upgrade Complete, SSH into any CVM and run ncc health_checks run_all 2>&1 | tee /home/nutanix/ncc_post_upgrade.log. Compare results against the pre-upgrade log. All checks should pass. Pay particular attention to: hardware checks, CVM service health, data path checks, and cluster resiliency status.
  15. Verify AOS Version: In Prism Element → Home, confirm the cluster summary shows the new AOS version on all nodes. From CLI, run ncli cluster version and hostssh "cat /etc/nutanix/release-version" to verify every host is on the correct version. Mismatched versions across nodes indicate a partial upgrade — investigate the upgrade task logs immediately.
  16. Validate Cluster Services: Run cluster status on any CVM — all services should show UP across all nodes. Check Prism Element dashboard for any red or yellow indicators. Verify storage performance metrics (IOPS, latency, throughput) have returned to baseline in the Analysis > Performance charts.
  17. Validate VM Workloads: Confirm all production VMs are powered on and applications are responding normally. Check with application owners that no services were disrupted. Review VM event logs in Prism Central or Prism Element for any unexpected restarts or HA events that occurred during the upgrade window.

Upgrade Prism Central (if applicable): After AOS is successfully upgraded on all clusters, upgrade Prism Central to a compatible version from Prism Central → Settings → Upgrade Software → Prism Central. Follow the same validation steps post-upgrade. Ensure PC version remains within the supported compatibility matrix relative to the newly upgraded AOS clusters.
  19. Clear Alerts & Update Documentation: Acknowledge and resolve any upgrade-related informational alerts in Prism Element and Prism Central. Update the CMDB and infrastructure runbook with the new AOS/AHV version, upgrade date, and engineer name. Retain the pre- and post-upgrade NCC logs for audit purposes.
  20. Communicate Completion: Send a post-upgrade notification to stakeholders and application owners confirming the upgrade completed successfully, all workloads are healthy, and the cluster is back in full production state. Nutanix Flow Micro-Segmentation

Nutanix · Security
  1. Prerequisites & Licensing: Confirm all Nutanix clusters managed by Prism Central are running AHV (Flow is AHV-only — not supported on ESXi). Verify Nutanix Flow licences are applied in Prism Central → Settings → Licensing. Ensure Prism Central is version 5.17 or later for full Flow feature support. Document which clusters and VMs are in scope for micro-segmentation.
  2. Enable Microsegmentation in Prism Central: Navigate to Prism Central → Settings → Microsegmentation → click Enable. Accept the confirmation prompt. This installs the Flow service on all registered AHV clusters. Monitor the task in the Tasks pane — enablement typically completes in 5–10 minutes. Verify the Flow icon appears in the left navigation menu once enabled.
  3. Understand Flow Policy Types: Before creating policies, choose the appropriate type: Application Security Policy — controls traffic for a defined multi-tier application (recommended for most workloads); Isolation Environment Policy — completely blocks all traffic between two groups of VMs regardless of other rules; Quarantine Policy — isolates a specific VM for forensic investigation while allowing limited access for remediation. Plan policy types per application during the design phase.
  4. Design the Category Taxonomy: Plan and document the category key-value pairs before creating them in Prism Central. Recommended structure: AppType: WebApp / Database / Middleware, AppTier: Web / App / DB, Environment: Production / Dev / Test / DMZ, Owner: TeamA / TeamB. Keep categories granular enough for policy control but not so granular they become unmanageable.
  5. Create Categories in Prism Central: Navigate to Administration → Categories → New Category. Enter the Key (e.g., AppTier) and add all relevant Values (e.g., Web, App, DB). Click Save. Repeat for each category key. Categories are cluster-agnostic and apply across all registered PE clusters. Avoid spaces or special characters in category names to prevent policy matching issues.
  6. Assign Categories to VMs: In Prism Central → Virtual Infrastructure → VMs, select one or more VMs → Actions → Manage Categories. Assign the appropriate key-value pairs (e.g., AppTier: Web and Environment: Production). For bulk assignments, use the Prism Central REST API or nuclei CLI: nuclei vm.update_category vm_name=<VM> categories="AppTier=Web". Verify assignments appear correctly on the VM detail page.
  7. Map Application Traffic Flows: Before writing rules, analyse actual traffic between application tiers using Prism Central → Flow → Traffic Visualisation (if available) or existing network monitoring tools. Document required flows: which ports/protocols Web tier opens to App tier, App tier to DB tier, and management access paths. This forms the basis for the allow-list rules in the security policy.
  8. Create an Application Security Policy (Monitor Mode): Go to Prism Central → Policies → Security → Create Security Policy → Secure Applications. Name the policy (e.g., CRM-App-Policy). Set the policy mode to Monitor first — this logs traffic without blocking, allowing you to validate rules without impacting production workloads. Assign the policy to the target application category.
  9. Define Inbound Rules: In the policy editor, add inbound rules for each source category or external IP/subnet: select source entity type (Category or Subnet), choose the source category (e.g., AppTier: Web), specify protocol (TCP/UDP/ICMP), and enter destination port(s) (e.g., TCP 8080 to the App tier). Use Allow All only for explicitly required broad access — avoid wildcards where possible.
  10. Define Outbound Rules: Add outbound rules for traffic the secured VMs initiate — e.g., App tier to DB tier on TCP 1433 (MSSQL) or TCP 3306 (MySQL); App tier to AD on TCP/UDP 389 (LDAP); all tiers to DNS on UDP 53. Ensure management access paths are included (e.g., TCP 22 from Jump Host subnet to all tiers). Missing outbound rules will block traffic once the policy is enforced.
  11. Configure Default Inbound/Outbound Behaviour: At the bottom of the policy editor, set the default action for traffic not matching any rule: choose Allow Rest of the Traffic for a permissive default during initial rollout, or Deny Rest of the Traffic for a strict deny-by-default posture once rules are fully validated. Always start with Allow in Monitor mode and transition to Deny only after rule validation in Enforce mode.
  12. Apply Policy in Monitor Mode & Observe Logs: Save and apply the policy. In Monitor mode, Flow logs all traffic matching and not matching the defined rules without dropping any packets. Review logs in Prism Central → Flow → Security Policies → select policy → Policy Hits. Look for unexpected traffic sources or missing allow rules indicated by Deny (Monitor) log entries. Adjust rules based on observed traffic over 24–72 hours.
  13. Create Isolation Environment Policy (if required): For strict network isolation between environments (e.g., Production and Dev must never communicate), go to Policies → Security → Create → Isolate Environments. Select the two category groups to isolate (e.g., Environment: Production vs Environment: Dev). Isolation policies override application policies — no traffic between the two groups will be permitted regardless of other rules.
  14. Create Quarantine Policy (if required): For incident response, define a Quarantine policy under Policies → Security → Create → Quarantine VMs. Set the quarantine mode — Strict (block all traffic) or Forensics (allow limited inbound from a designated forensics subnet). To quarantine a compromised VM, assign it the Quarantine: Strict or Quarantine: Forensics category — the policy takes effect immediately without requiring a policy edit.
  15. Transition Policy to Enforce Mode: After validating all rules in Monitor mode and confirming no legitimate traffic is being flagged as Deny (Monitor), edit the policy and change the mode from Monitor to Apply (Enforce). Save and apply. Flow will now actively drop traffic that does not match allow rules. Communicate the enforcement window to application teams before switching modes.
  16. Validate Enforcement with Traffic Tests: From a VM in the Web tier, test connectivity: curl http://<App-tier-IP>:8080 should succeed; curl http://<DB-tier-IP>:3306 should fail (blocked by policy). Use nc -zv <IP> <port> for port-level testing. Confirm blocked traffic appears in Flow policy hit logs as Deny (Enforce). Adjust rules if legitimate traffic is being dropped unexpectedly.
  17. Monitor Ongoing Policy Hits: Regularly review Prism Central → Policies → Security for policy hit counts and recent deny events. Set up alert policies in Prism Central to notify the security team when unexpected deny events spike — this can indicate a misconfiguration, a new application dependency, or an active lateral movement attempt.
  18. Integrate with Security Tools (Optional): Configure Prism Central to forward Flow logs and security events to your SIEM (e.g., Splunk, QRadar, Microsoft Sentinel) via syslog. In Prism Central → Settings → Syslog Server, add the SIEM collector IP and port. Flow policy hit data in the SIEM enables correlation with other security events and compliance reporting.
  19. Manage Policy Lifecycle: Establish a policy review cadence (quarterly recommended). When new application tiers or VMs are added, assign categories immediately and review existing policies to include new flows. Use Prism Central REST API to automate category assignment as part of VM provisioning workflows (Calm blueprints or third-party orchestration tools). Remove obsolete rules when application components are decommissioned.
  20. Document & Audit: Export all security policies and category assignments from Prism Central (Settings → Policy Export or via REST API). Document the policy design rationale, category taxonomy, rule logic, and enforcement dates in the security runbook. Retain policy change history for compliance audits (PCI-DSS, ISO 27001, HIPAA). Schedule periodic reviews to ensure policies remain aligned with the current application architecture.

Linux

Linux server administration, shell scripting, and system management procedures

Linux File System Tree

Linux · Administration
  1. / (Root): Top-level directory — the starting point of the entire Linux file system hierarchy; all other directories branch from here
  2. /bin & /sbin: Essential user binaries (ls, cp, mv) and system binaries (fdisk, ifconfig) required for booting and single-user mode
  3. /etc: System-wide configuration files (network, users, services); critical files include /etc/passwd, /etc/fstab, /etc/hosts, /etc/ssh/sshd_config
  4. /var: Variable data that changes at runtime — logs (/var/log), mail spools, cron jobs, and package manager databases
  5. /home & /root: User home directories (/home/username) for personal files and settings; /root is the home directory for the root superuser
  6. /tmp & /opt: /tmp holds temporary files cleared on reboot; /opt stores optional third-party software packages installed outside the default tree
  7. /proc & /sys: Virtual filesystems exposing kernel and hardware info in real time — use cat /proc/cpuinfo, /proc/meminfo, and /sys for device tuning
  8. /dev & /mnt: /dev contains device files (disks, TTYs, null); /mnt and /media are standard mount points for external drives and network shares

Linux Permission

Linux · Security
  1. Understanding Permissions: Every file has three permission sets — Owner (u), Group (g), Others (o); each with Read (r=4), Write (w=2), Execute (x=1) rights
  2. View Permissions: Run ls -l to list permissions; output format is -rwxr-xr-- where the first char is file type, followed by three triads (owner/group/others)
  3. chmod (Symbolic): Use chmod u+x file to add execute for owner, chmod g-w file to remove write from group, chmod o=r file to set others to read-only
  4. chmod (Numeric): Use octal notation — chmod 755 file sets rwxr-xr-x; chmod 644 file sets rw-r--r--; chmod 700 file restricts access to owner only
  5. chown & chgrp: Change file owner with chown user:group file; use chown -R user:group /dir for recursive ownership changes on directories
  6. Special Permissions: Set SUID (chmod u+s) to run as file owner, SGID (chmod g+s) to inherit group, Sticky Bit (chmod +t) on directories to restrict deletion to file owners only
  7. umask: Set default permission mask with umask 022 (new files get 644, directories get 755); add to /etc/profile or ~/.bashrc to persist across sessions
  8. ACL (Advanced): Use setfacl -m u:username:rwx file for fine-grained access beyond standard UGO; verify with getfacl file

File Systems Concept

Linux · Storage
  1. What is a File System: A file system defines how data is stored, organized, and retrieved on a disk — it manages inodes (metadata), data blocks, and directory structures
  2. Common Types: ext4 (default on most Linux distros — journaled, stable), XFS (high-performance, large files), Btrfs (snapshots, checksums), tmpfs (RAM-based, volatile), NFS (network-mounted)
  3. Inodes & Blocks: Each file has an inode storing metadata (permissions, owner, timestamps, pointers to data blocks); check inode usage with df -i and block usage with df -h
  4. Create a File System: After partitioning, format with mkfs.ext4 /dev/sdb1 or mkfs.xfs /dev/sdb1; use blkid to verify the UUID and type of the new file system
  5. Mount & Unmount: Mount with mount /dev/sdb1 /mnt/data; unmount with umount /mnt/data; verify active mounts using mount | grep sdb1 or lsblk
  6. Persistent Mounts (/etc/fstab): Add entry — UUID=xxxx /mnt/data ext4 defaults 0 2; test without rebooting using mount -a and check for errors
  7. Check & Repair: Run fsck /dev/sdb1 on unmounted partitions to detect and fix errors; use tune2fs -l /dev/sdb1 to inspect ext4 superblock details
  8. Disk Usage & Quotas: Monitor usage with du -sh /path and df -h; enable disk quotas via quotaon and define limits with edquota -u username to control per-user consumption

Install & Configure YUM

Linux · Package Management
  1. Check Existing YUM: Verify if YUM is already installed by running yum --version; YUM is pre-installed on RHEL, CentOS 7, and Amazon Linux — if found, proceed to configuration steps
  2. Install YUM (if missing): On minimal installs, run sudo rpm -ivh yum-*.rpm using the RPM from your distro's ISO, or bootstrap with sudo dnf install yum -y on RHEL 8/9 where DNF is the default
  3. Verify Package Manager: Confirm installation with which yum (should return /usr/bin/yum) and check version details via yum --version
  4. Configure YUM Repos: Repo files live in /etc/yum.repos.d/; each .repo file defines a repository with [repo-id], name, baseurl or mirrorlist, and enabled=1 / gpgcheck=1
  5. Add EPEL Repository: Install Extra Packages for Enterprise Linux with sudo yum install epel-release -y; this unlocks thousands of additional packages not in the base repo
  6. Clean & Rebuild Cache: Run sudo yum clean all to remove cached metadata, then sudo yum makecache to rebuild the local package index from all enabled repos
  7. Update System: Apply all available updates with sudo yum update -y; use sudo yum update <package-name> to update a specific package only
  8. Install & Remove Packages: Install with sudo yum install <package> -y; remove with sudo yum remove <package> -y; use sudo yum reinstall <package> to fix corrupted installs
  9. Search & Info: Search available packages with yum search <keyword>; inspect package details (version, dependencies, size) with yum info <package> before installing
  10. YUM Groups & History: Install predefined software groups with sudo yum groupinstall "Development Tools" -y; review and roll back transactions using yum history list and yum history undo <id>

Install & Configure Nginx

Linux · Web Server

Create EC2 Instance

AWS · Compute
  1. Sign in to AWS Console: Navigate to console.aws.amazon.com, sign in with your IAM credentials, and ensure you are in the correct region (top-right region selector) before creating the instance — resources are region-specific
  2. Open EC2 Dashboard: Search for EC2 in the services menu → click EC2 → on the Dashboard click Launch Instance; review running instance count and limits before proceeding to avoid hitting service quotas
  3. Name & Tags: Enter a meaningful instance name and add resource tags — at minimum set Name, Environment (dev/staging/prod), Owner, and CostCenter; tags are critical for billing visibility, automation, and governance at scale
  4. Choose Amazon Machine Image (AMI): Select from Quick Start (Amazon Linux 2023, Ubuntu, Windows), My AMIs (custom golden images), or AWS Marketplace; prefer the latest AWS-maintained AMIs for up-to-date security patches and compatibility
  5. Select Instance Type: Choose based on workload requirements — t3.micro/t3.small for dev/test, t3.medium for light production, m6i.large for general-purpose, c6i for compute-heavy, r6i for memory-intensive; use the Compare Instance Types link to evaluate options
  6. Set Up Key Pair: Select an existing key pair or create a new one; download the .pem file and store it securely (chmod 400 on Linux); this is the only authentication method for SSH — loss of the key means loss of direct instance access
  7. Configure Network: Select your VPC and the appropriate subnet (public subnet for internet-accessible instances, private for backend); enable Auto-assign Public IP only for internet-facing instances; select or create a Security Group with least-privilege inbound rules
  8. Configure Storage: Set the root EBS volume size (minimum 20 GB recommended for production); choose gp3 volume type for best price-performance; enable Delete on Termination only for non-persistent data; enable EBS encryption with a KMS key for all sensitive workloads
  9. Advanced Details: Assign an IAM Instance Profile for AWS service access (S3, SSM, CloudWatch); optionally add User Data script for bootstrapping (install packages, configure services at first boot); set Termination Protection to enabled for production instances
  10. Review & Launch: Verify all settings in the Summary panel — AMI, instance type, key pair, VPC, subnet, security group, and storage; click Launch Instance and wait for status checks to show 2/2 passed before connecting or deploying applications

Launch an EC2 Instance

AWS · Compute
  1. Open EC2 Console: Log in to AWS Console → EC2 → Launch Instance; choose a descriptive Name tag — critical for identifying instances in large environments
  2. Select AMI: Choose an Amazon Machine Image — Amazon Linux 2023 for general workloads, Ubuntu 22.04 LTS for dev/web servers, Windows Server 2022 for .NET apps; prefer AWS-maintained AMIs for patched baselines
  3. Choose Instance Type: Select instance family based on workload — t3/t4g (burstable, dev/test), m6i (general purpose), c6i (compute-intensive), r6i (memory-intensive); check vCPU and RAM against your requirements
  4. Configure Key Pair: Create or select an existing key pair (.pem for Linux SSH, .ppk for PuTTY); store the private key securely — AWS does not retain a copy; without it, Linux instance access is lost permanently
  5. Network Settings: Select the VPC and subnet (public for internet-facing, private for internal); enable Auto-assign Public IP for public instances; create or assign a Security Group with required inbound rules (SSH 22, HTTP 80, HTTPS 443)
  6. Configure Storage: Set root EBS volume size (default 8 GB for Amazon Linux — increase to 20-30 GB for production); select gp3 for cost-effective SSD performance; enable encryption using AWS KMS key
  7. Add User Data (Optional): Scroll to Advanced Details → User Data; paste a bootstrap script (e.g. install Nginx on first boot); script runs as root at launch — use for automated software installation and configuration
  8. Assign IAM Role: Under Advanced Details → IAM Instance Profile, attach a role granting the instance access to AWS services (S3, SSM, CloudWatch) without storing credentials on the instance
  9. Launch & Connect: Review summary and click Launch Instance; wait for Instance State to show Running and Status Checks to pass 2/2; connect via EC2 Instance Connect, SSH with key pair, or AWS Systems Manager Session Manager
  10. Post-Launch Validation: Verify connectivity, install updates, confirm attached IAM role permissions, set up CloudWatch agent for metrics and logs, and add Name/Environment/Owner tags for governance

S3 Bucket Setup & Policy Configuration

AWS · Storage
  1. Create S3 Bucket: AWS Console → S3 → Create Bucket; choose a globally unique name (lowercase, hyphens allowed); select the AWS Region closest to your users or application; bucket names cannot be changed after creation
  2. Block Public Access: By default all public access is blocked — keep this enabled for private data; only disable specific settings if hosting a static website or requiring public object access; document any exceptions
  3. Enable Versioning: Bucket Properties → Versioning → Enable; versioning protects against accidental deletion and overwrites; once enabled it can only be suspended, not disabled; combine with lifecycle rules to control storage costs
  4. Enable Encryption: Properties → Default Encryption → Enable; choose SSE-S3 (AWS-managed keys, free) or SSE-KMS (customer-managed keys via AWS KMS, additional cost but audit trail); enforce encryption via bucket policy denying unencrypted uploads
  5. Configure Bucket Policy: Permissions → Bucket Policy → Policy Editor; write JSON policy granting or denying access by Principal (IAM user/role/account), Action (s3:GetObject, s3:PutObject), and Resource (specific bucket ARN or prefix)
  6. Static Website Hosting: Properties → Static Website Hosting → Enable; set index document (index.html) and error document (error.html); disable Block Public Access and add a bucket policy allowing s3:GetObject for all principals
  7. Set Up Lifecycle Rules: Management → Lifecycle Rules → Create; transition objects to S3 Standard-IA after 30 days, Glacier after 90 days, and expire (delete) after 365 days; apply to entire bucket or a specific prefix/tag
  8. Enable Access Logging: Properties → Server Access Logging → Enable; specify a target bucket (separate from source) and prefix; logs capture requester, bucket, request time, action, response status — essential for auditing and troubleshooting
  9. Configure CORS (if needed): Permissions → CORS → Edit; add a JSON rule defining AllowedOrigins, AllowedMethods (GET, PUT), and AllowedHeaders; required when a web app on a different domain reads or writes S3 objects directly
  10. Test & Validate: Upload a test object and verify access using the S3 Console or AWS CLI (aws s3 cp file.txt s3://bucket-name/); confirm bucket policy restrictions with the IAM Policy Simulator before production use

Create & Configure a VPC

AWS · Networking
  1. Plan CIDR Block: Design your IP address space before creating — use a /16 block (e.g. 10.0.0.0/16 = 65,536 IPs) for flexibility; avoid overlapping with on-premises ranges if VPN/Direct Connect is planned; document subnet allocation upfront
  2. Create the VPC: AWS Console → VPC → Your VPCs → Create VPC; enter name tag and IPv4 CIDR block; enable DNS Resolution and DNS Hostnames — required for services like RDS and ECS to resolve correctly
  3. Create Subnets: VPC → Subnets → Create Subnet; create at least one public subnet (e.g. 10.0.1.0/24) and one private subnet (e.g. 10.0.2.0/24) per Availability Zone; distribute across 2-3 AZs for high availability
  4. Create & Attach Internet Gateway: VPC → Internet Gateways → Create IGW → name it and attach to your VPC; one IGW per VPC; the IGW enables outbound internet access for public subnets and inbound access for internet-facing resources
  5. Configure Route Tables: Create a Public Route Table — add a route 0.0.0.0/0 pointing to the IGW and associate public subnets; leave the Private Route Table with local route only; private subnets route internet traffic through a NAT Gateway instead
  6. Deploy NAT Gateway: VPC → NAT Gateways → Create; place it in a public subnet and allocate an Elastic IP; update the private route table with 0.0.0.0/0 pointing to the NAT Gateway; deploy one NAT GW per AZ for high availability
  7. Configure Security Groups: VPC → Security Groups → Create; define inbound rules (e.g. allow HTTPS 443 from 0.0.0.0/0 for web tier, allow 3306 from app-sg for DB tier); security groups are stateful — return traffic is allowed automatically
  8. Configure Network ACLs: VPC → Network ACLs → Edit inbound/outbound rules; NACLs are stateless — you must explicitly allow both inbound and outbound for each flow; use NACLs as a subnet-level firewall for coarse-grained traffic control
  9. Enable VPC Flow Logs: VPC → select VPC → Flow Logs → Create; publish to CloudWatch Logs or S3; capture ACCEPT/REJECT traffic at VPC, subnet, or ENI level; essential for security auditing, troubleshooting, and compliance requirements
  10. Validate Connectivity: Launch test EC2 instances in public and private subnets; verify public instance reaches internet via IGW; verify private instance reaches internet via NAT GW; test inter-subnet communication and confirm Security Group rules behave as expected

Route 53 DNS Management

AWS · Networking
  1. Access Route 53 Console: Log in to AWS Console → search Route 53; note that Route 53 is a global service — hosted zones and records are not region-specific; ensure your IAM user has the AmazonRoute53FullAccess policy attached
  2. Register or Transfer a Domain: Route 53 → Registered Domains → Register Domain; search for your desired domain name, add to cart, and complete registration; for existing domains, choose Transfer Domain and follow the registrar unlock and auth-code process
  3. Create a Hosted Zone: Route 53 → Hosted Zones → Create Hosted Zone; enter your domain name and choose Public (internet-facing) or Private (internal VPC resolution); AWS automatically creates SOA and NS records — note the 4 Name Servers assigned
  4. Update Name Servers: If your domain is registered outside AWS, log in to your registrar (GoDaddy, Namecheap, etc.) and replace the default name servers with the 4 Route 53 NS values; DNS propagation typically takes 24–48 hours globally
  5. Create DNS Records: Inside the Hosted Zone → Create Record; add an A record pointing your root domain to an IP or load balancer, a CNAME for subdomains (e.g. www → yourdomain.com), MX records for email routing, and TXT records for domain verification (SPF, DKIM)
  6. Configure Alias Records: Use Alias records (Route 53-specific) instead of CNAMEs for root domains; Alias records can point directly to AWS resources — Application Load Balancers, CloudFront distributions, S3 static websites, and API Gateway endpoints — with no extra charge for queries
  7. Set Up Routing Policies: Choose a routing policy per record — Simple (default, single value), Weighted (A/B traffic split by percentage), Latency-based (routes to lowest-latency region), Failover (active/passive with health checks), or Geolocation (route by user country/continent)
  8. Configure Health Checks: Route 53 → Health Checks → Create; set protocol (HTTP/HTTPS/TCP), endpoint (IP or domain), path (e.g. /health), and check interval (30s standard, 10s fast); attach health checks to Failover or Weighted records to automatically remove unhealthy endpoints
  9. Enable DNS Query Logging: Hosted Zone → Configure Query Logging → select or create a CloudWatch Log Group; logs capture query name, type, response code, and resolver IP — useful for traffic analysis, debugging resolution failures, and security auditing
  10. Test & Validate: Use the Route 53 Test Record Set tool (Hosted Zone → Test record set) to simulate DNS queries; validate externally with CLI tools — dig yourdomain.com, nslookup yourdomain.com, or host yourdomain.com — and confirm TTL, record values, and routing behaviour are correct

Auto Scaling Group Configuration

AWS · Compute
  1. Prerequisites: Ensure you have a working AMI (or launch template), a VPC with at least 2 subnets across different AZs, and a configured Security Group before creating the ASG
  2. Create a Launch Template: EC2 → Launch Templates → Create; define AMI, instance type, key pair, IAM role, Security Group, and User Data bootstrap script; versioning is supported — always use the latest version in the ASG
  3. Create Auto Scaling Group: EC2 → Auto Scaling Groups → Create; name the ASG, select the Launch Template and version; choose VPC and select multiple subnets across AZs for high availability and fault tolerance
  4. Attach Load Balancer: In the ASG wizard, attach an existing Application Load Balancer target group or create one; enable ELB health checks so the ASG replaces instances that fail load balancer health checks, not just EC2 status checks
  5. Set Capacity Limits: Define Minimum (floor — ASG never scales below this), Maximum (ceiling — ASG never exceeds this), and Desired (current target count) capacity; start with min=2, desired=2, max=6 for a typical production workload
  6. Configure Scaling Policies: Choose Target Tracking (simplest — e.g. keep average CPU at 50%), Step Scaling (scale by fixed increments based on CloudWatch alarm thresholds), or Scheduled Scaling (scale up before known traffic spikes like business hours or events)
  7. Set Cooldown Period: Default cooldown is 300 seconds — prevents the ASG from launching or terminating additional instances before the previous scaling activity takes effect; tune lower (60–120s) for faster-responding workloads
  8. Configure Instance Refresh: ASG → Instance Refresh → Start; set minimum healthy percentage (e.g. 80%) and warm-up time; use this to safely roll out new AMI versions or launch template changes across the fleet without downtime
  9. Enable Lifecycle Hooks: Add Launch and Terminate hooks to run custom actions (install agents, drain connections, back up logs) before an instance is put into service or removed; hooks pause the instance in a Pending:Wait or Terminating:Wait state
  10. Test & Monitor: Manually set desired capacity to trigger a scale-out; verify new instances register with the load balancer and pass health checks; monitor ASG activity history, CloudWatch metrics (GroupDesiredCapacity, GroupInServiceInstances), and SNS notifications for scaling events

CloudWatch Monitoring & Alerts

AWS · Monitoring
  1. Access CloudWatch Console: AWS Console → CloudWatch; CloudWatch is a regional service — switch to the correct region; it collects metrics, logs, events, and traces from virtually all AWS services automatically
  2. Explore Default Metrics: CloudWatch → Metrics → All Metrics; browse namespaces (AWS/EC2, AWS/RDS, AWS/ELB, etc.); key EC2 metrics include CPUUtilization, NetworkIn/Out, DiskReadOps — note that memory and disk usage require the CloudWatch Agent
  3. Install CloudWatch Agent: On EC2, install the agent via Systems Manager (Run Command → AWS-ConfigureAWSPackage → AmazonCloudWatchAgent) or manually; configure with wizard (sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-config-wizard) to collect memory, disk, and custom app metrics
  4. Create a Dashboard: CloudWatch → Dashboards → Create Dashboard; add widgets (Line, Number, Gauge, Bar); pin key metrics like CPU, memory, request count, error rate, and latency across services; share dashboards across accounts using cross-account observability
  5. Create a CloudWatch Alarm: Metrics → select metric → Create Alarm; set the threshold (e.g. CPUUtilization > 80% for 2 consecutive 5-minute periods); define alarm states: OK, ALARM, INSUFFICIENT_DATA; alarms can trigger SNS, Auto Scaling, or EC2 actions
  6. Set Up SNS Notifications: Create an SNS Topic (Simple Notification Service → Create Topic → Standard); add email/SMS/Lambda subscriptions; confirm the email subscription; attach the SNS topic to CloudWatch Alarms to receive immediate alerts on threshold breaches
  7. Configure Log Groups: CloudWatch → Log Groups → Create; applications and AWS services push logs here; set retention period (7, 14, 30, 90 days) to control storage costs; use log groups per application/environment (e.g. /prod/nginx/access, /prod/app/errors)
  8. Create Metric Filters: Log Groups → select group → Metric Filters → Create; define a filter pattern (e.g. ERROR or [status=5*, ...]) to extract numeric metrics from log data; publish the metric to a custom namespace and set it as the basis for an alarm
  9. Set Up CloudWatch Synthetics: CloudWatch → Synthetics → Create Canary; write or use a blueprint script to simulate user journeys (check URL availability, API responses, login flows); canaries run on a schedule and alarm when endpoints fail or latency exceeds thresholds
  10. Enable CloudWatch Container Insights: For ECS/EKS workloads, enable Container Insights in cluster settings; it provides CPU, memory, network, and storage metrics per task/pod; use Contributor Insights to identify top-N contributors to high traffic or error rates in logs and metrics

Elastic Load Balancer Setup

AWS · Networking
  1. Choose Load Balancer Type: Application Load Balancer (ALB) for HTTP/HTTPS and path/host-based routing; Network Load Balancer (NLB) for TCP/UDP with ultra-low latency and static IPs; Gateway Load Balancer (GWLB) for inline network appliances like firewalls
  2. Create the Load Balancer: EC2 → Load Balancers → Create; select ALB; enter a name, choose Internet-facing (public) or Internal (private VPC); select at least 2 Availability Zones and their public subnets for high availability
  3. Configure Security Groups: Create or assign a Security Group to the ALB allowing inbound HTTP (80) and HTTPS (443) from 0.0.0.0/0; EC2 instance Security Groups should allow traffic only from the ALB Security Group — never expose instance ports directly to the internet
  4. Create a Target Group: EC2 → Target Groups → Create; choose target type (Instances, IP addresses, or Lambda); set protocol (HTTP), port (e.g. 80), and VPC; configure health check path (e.g. /health), healthy threshold (2), unhealthy threshold (3), and interval (30s)
  5. Register Targets: Select EC2 instances or IPs to add to the target group; set the port each target receives traffic on; newly registered targets enter an Initial state and become Healthy after passing the configured number of consecutive health checks
  6. Configure Listeners & Rules: ALB → Listeners → Add Listener; HTTP:80 — add a redirect rule to HTTPS:443; HTTPS:443 — add forward rule to your target group; add path-based rules (e.g. /api/* → API target group, /* → web target group) for microservice routing
  7. Attach SSL Certificate: HTTPS listener → select certificate from AWS Certificate Manager (ACM); request a free public certificate in ACM by validating domain ownership via DNS (add CNAME record) or email; ACM auto-renews certificates before expiry
  8. Enable Sticky Sessions (if needed): Target Group → Attributes → Stickiness → Enable; choose Load Balancer-generated cookie (AWSALB) or Application cookie; set duration; use only for stateful apps — stateless architectures with shared session stores (Redis/DynamoDB) are preferred
  9. Enable Access Logs: Load Balancer → Attributes → Access Logs → Enable; specify an S3 bucket with the correct bucket policy; logs capture client IP, request time, target, response codes, and latency — essential for troubleshooting and security analysis
  10. Test & Monitor: Copy the ALB DNS name and test in a browser or with curl; verify requests are distributed across targets; monitor CloudWatch metrics — RequestCount, TargetResponseTime, HTTPCode_ELB_5XX_Count, HealthyHostCount — and set alarms on unhealthy host count and 5xx errors

RDS Database Setup

AWS · Database
  1. Choose Database Engine: AWS Console → RDS → Create Database; select engine — MySQL, PostgreSQL (most popular open-source options), MariaDB, Oracle, SQL Server, or Amazon Aurora (MySQL/PostgreSQL-compatible with up to 5x performance improvement)
  2. Select Deployment Option: Choose Standard Create for full control; select Multi-AZ DB Instance for production (synchronous standby replica in a second AZ for automatic failover); use Single-AZ only for dev/test to reduce costs
  3. Configure Instance Class: Select DB instance class — db.t3.micro (free tier, dev/test), db.t3.medium (light production), db.m6i.large (general production), db.r6i.large (memory-intensive); match vCPU and RAM to your query load and connection count
  4. Set Storage: Choose General Purpose SSD (gp3) for most workloads; set allocated storage (minimum 20 GB); enable Storage Autoscaling with a maximum threshold to prevent out-of-space errors during unexpected growth; enable encryption at rest using AWS KMS
  5. Configure Connectivity: Select VPC and subnet group (create a DB Subnet Group with subnets in at least 2 AZs); set Public Accessibility to No for production; create or assign a VPC Security Group allowing inbound on the DB port (3306 MySQL, 5432 PostgreSQL) only from app-tier Security Groups
  6. Set Credentials: Enter a master username and a strong master password (or let AWS manage it via Secrets Manager — recommended); store credentials in AWS Secrets Manager for automatic rotation and secure retrieval by applications without hardcoding passwords
  7. Configure Backups: Set automated backup retention period (7–35 days); choose a backup window during low-traffic hours; enable point-in-time recovery (PITR) allowing restore to any second within the retention window; create manual snapshots before major changes
  8. Enable Enhanced Monitoring & Logs: Enable Enhanced Monitoring (1–60 second granularity for OS metrics); enable CloudWatch Logs export (error log, slow query log, general log); set slow query threshold to identify and optimise poorly performing queries
  9. Create Read Replicas (if needed): RDS → select DB → Actions → Create Read Replica; read replicas offload SELECT queries from the primary, improving read throughput; promote a read replica to standalone if you need to scale writes or recover from a regional failure
  10. Connect & Validate: Use the RDS endpoint (found in Connectivity tab) to connect from an EC2 instance in the same VPC — test with mysql -h endpoint -u admin -p or psql -h endpoint -U admin; verify Security Group rules, subnet routing, and parameter group settings if connection fails

CloudFront CDN Configuration

AWS · Networking
  1. Understand CloudFront: CloudFront is AWS's global CDN with 400+ edge locations worldwide; it caches content close to users to reduce latency, offloads origin traffic, provides DDoS protection via AWS Shield Standard, and integrates natively with S3, ALB, API Gateway, and custom HTTP origins
  2. Create a Distribution: AWS Console → CloudFront → Create Distribution; CloudFront has two delivery methods — Web (HTTP/HTTPS for websites and APIs) and RTMP (deprecated, for streaming); select Web for all modern use cases
  3. Configure Origin: Set the Origin Domain — S3 bucket URL for static sites (use the REST endpoint, not the website endpoint), ALB DNS name for dynamic apps, or a custom HTTP server; for S3, enable Origin Access Control (OAC) to restrict bucket access exclusively to CloudFront — never expose the bucket publicly
  4. Set Default Cache Behaviour: Define the Viewer Protocol Policy (Redirect HTTP to HTTPS — always enable); set Allowed HTTP Methods (GET/HEAD for static content, GET/HEAD/POST/PUT/DELETE for APIs); configure Cache Policy (CachingOptimized for static, CachingDisabled for dynamic/API content)
  5. Configure Cache Settings: Use managed cache policies (CachingOptimized sets TTL 1 day to 1 year) or create a custom policy; set minimum, default, and maximum TTL; use Cache-Control headers from your origin to control per-object TTL; configure origin request policies to forward headers, cookies, and query strings selectively
  6. Add Custom Domain & SSL: Distribution Settings → Alternate Domain Names (CNAMEs) → add your domain (e.g. cdn.yourdomain.com); select Custom SSL Certificate from ACM — the certificate must be in us-east-1 (N. Virginia) regardless of your distribution's region; create a CNAME record in Route 53 pointing to the CloudFront distribution domain
  7. Enable Compression: Cache Behaviour → Compress Objects Automatically → Yes; CloudFront automatically compresses text-based files (HTML, CSS, JS, JSON) with Gzip and Brotli if the viewer supports it; reduces transfer size by 60–80% improving load times and reducing data transfer costs
  8. Set Up WAF Integration: Associate an AWS WAF Web ACL with the distribution to block common web exploits (SQL injection, XSS, bad bots); use AWS Managed Rules for instant protection; WAF rules are evaluated at edge locations before requests reach your origin
  9. Configure Geo-Restriction: Distribution → Security → Geo-Restriction → Edit; create an allowlist (only specified countries can access) or blocklist (deny specific countries); useful for licensing compliance, regulatory requirements, or blocking known high-risk regions
  10. Invalidate Cache & Monitor: After deploying new content, create an invalidation (Invalidations → Create → path /* or specific files) to purge cached objects from all edge locations; monitor with CloudWatch metrics — Requests, BytesDownloaded, 4xxErrorRate, 5xxErrorRate, CacheHitRate — and enable CloudFront access logs to S3 for detailed analysis
